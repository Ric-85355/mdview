## Цель проекта

Лёгкий read-only просмотрщик Markdown-файлов с Python- и C-
TUI-реализациями для Linux, самостоятельной Android-реализацией
и поэтапно развиваемой PHP/vanilla-JS Web-версией.

Основной сценарий использования — чтение технической документации и справочных Markdown-файлов с быстрым переходом между разделами через оглавление и поиском по тексту.

## C-версия

В ветке `main` рядом с Python-версией размещена C-реализация,
функционально выровненная с локальным Python Reader. Python-only Repository
View в C на текущем этапе не переносится.

Структура C-версии:

- `c-src/mdview_model.c` и `c-src/mdview_model.h` — UTF-8 документ, Markdown-
  преобразования, source mapping, визуальные строки и поиск;

- `c-src/mdview_c.c` — `ncursesw` TUI, состояние панелей и навигация;

- `tests/c/test_mdview_model.c` — автономные тесты модели без curses;

- `tests/c/test_cli.sh` — проверки CLI и ошибок;

- `tests/compare_models.py` и `tests/fixtures/parity.md` — прямое сравнение
  текста, стилей, source lines и offsets C-модели с Python-эталоном;

- `tests/pty_smoke.py` — UTF-8 PTY smoke-тест TUI, поиска, resize и
  восстановления терминала;

- `Makefile` — сборка `build/mdview-c` и тестов.

Историческая ветка `c-version` с ранним C-портом сохраняется отдельно.

## Android-версия

В `android/` находится самостоятельное приложение Kotlin/Jetpack Compose версии
`0.1.0`, minSdk 28, compileSdk/targetSdk 35. Оно не использует код TUI-версий.

Структура:

- `markdown/` — модель, однопроходный минимальный Markdown-парсер и поиск;

- `data/` — чтение `content://`/`file://` URI и SharedPreferences-хранилище
  позиций с SHA-256 ключом из URI;

- `ui/ViewerViewModel.kt` — единое состояние позиции/текущего раздела, оглавления, поиска и
  восстановления при повороте;

- `ui/MdviewApp.kt` — Compose UI, LazyColumn документа, отдельная область оглавления,
  double tap, поиск и системные темы;

- `MainActivity.kt` — `OpenDocument` picker, `ACTION_VIEW`/Open with, `ACTION_SEND`/Share
  и URI access без преобразования `content://` в filesystem path.

Реализованы H1–H6 в документе, H1–H3 в оглавлении, абзацы, списки,
bold, italic, inline/fenced code и визуальное оформление ссылок. Есть поиск с
циклической навигацией и подсветкой, обратная синхронизация оглавления,
закрытие оглавления по double tap и позиция для каждого URI. Ссылки пока не открываются;
таблицы, изображения и сложный CommonMark не поддержаны.

При закрытии Android-поиска текущая позиция чтения сохраняется, а запрос и
подсветка очищаются. Длинные fenced code blocks имеют ограниченный внутренний
viewport; навигация поиска прокручивает его к конкретному текущему совпадению.

Внизу главного Android-экрана постоянно зарезервирована отдельная зона высотой
50 dp с локальным `AdBannerPlaceholder`. Это только UX-заглушка: рекламная сеть,
сетевые разрешения, tracking, advertising ID и consent SDK не подключены. Зона
уменьшает высоту области чтения и никогда на неё не накладывается.

Верхняя зона Android Reader всегда состоит из двух компактных строк. В первой
расположены Material-кнопка Back, центральная `Contents` / `TOC N` и Material-иконка Search;
во второй всегда показано имя текущего документа. При закрытом TOC центральная кнопка
показывает `Contents` без номера и открывает оглавление. При открытом TOC она показывает
`TOC 1`/`TOC 2`/`TOC 3` и циклически меняет глубину. Выбранная глубина хранится в `SavedStateHandle`
и не сбрасывается при закрытии. Свайпы управления и отдельная кнопка закрытия удалены;
оглавление закрывается double tap по видимому тексту.

`DocumentSectionResolver` вычисляет текущий видимый заголовок по блоку документа и глубине.
Единая текущая позиция обновляется при ручной прокрутке, TOC-тапе, переходе поиска и восстановлении.
При скрытом H2/H3 выбирается ближайший видимый родитель; TOC-список прокручивается к текущему пункту, если он не виден.

Оглавление больше не overlay: при открытии оно занимает до 48% высоты `ReaderBody` как обычный
верхний элемент вертикального layout, а текст получает оставшуюся высоту. Один и тот же `LazyListState`
сохраняет индекс и offset первого видимого элемента при открытии/закрытии, а постоянная верхняя
зона не меняет эту модель. Поиск прокручивает саму текстовую
область, поэтому текущее совпадение не может оказаться под TOC.

Сборка: JDK 17, Android SDK API 35, `cd android && ./gradlew
testDebugUnitTest assembleDebug lintDebug`. APK: `android/app/build/outputs/apk/debug/app-debug.apk`.

### Android Repository/Upload срез

Android-версия теперь имеет один настраиваемый HTTPS/SFTP-репозиторий.
`RepositoryViewModel` управляет экранами Repository/Reader/Settings, загруженным
индексом, текущим относительным путём и одной сетевой/SFTP-операцией. Путь
хранится в `SavedStateHandle`. Repository View теперь однооконный: во вложенной
папке первым идёт `..`, затем дочерние каталоги, затем Markdown-документы; tap
заменяет список содержимым каталога либо открывает документ в Reader. Breadcrumbs
и двухпанельного режима нет. Строки используют компактные штатные Material Icons:
стрелку вверх для `..`, папку для каталога и документ для `.md`, без emoji.
Format-1 parser поддерживает документы и каталоги
рядом, корень и два уровня каталогов, отклоняя unsafe paths. Refresh заново находит
точную папку по сохранённому relative path или возвращается к ближайшему
существующему родителю; ошибка не уничтожает старый индекс.

Верхняя панель Repository содержит alias и единый Menu: Refresh, Upload,
New folder, Settings. New folder создаёт один безопасный дочерний каталог через
SFTP. Long press по каталогу или документу открывает компактное Rename/Delete;
для `..` контекстного меню нет. Rename не меняет parent и не перезаписывает
существующий target. Документ остаётся case-insensitive `.md`; каталог принимает
только один непустой basename. Удаление файла требует подтверждения, а каталог
удаляется только после SFTP-проверки пустоты. Recursive delete, copy/move,
multi-select и редактор файлов не реализованы.

Settings хранит `name`, `repository_url`, HTTP user и SFTP enabled/host/port/user/root
в private SharedPreferences. HTTP/SFTP passwords хранятся только как AES/GCM ciphertext;
неэкспортируемый AES-256 key создаётся в Android Keystore. Пароли не показываются
после сохранения и не пишутся в Logcat. `RepositoryHttpClient` на `HttpURLConnection` одинаково
применяет optional Basic authentication к `repository.json` и документам. Удалённый Markdown
парсится в `ViewerViewModel.openSource()` и открывается в прежнем Reader с поиском, TOC,
темами и позицией по stable HTTP URL.

Upload использует Android `OpenDocument`, `ContentResolver` и `OpenableColumns.DISPLAY_NAME`.
Принимается только case-insensitive `.md` basename без separators/traversal. SFTP destination
строится только из `sftp_root`, текущего repository-relative path и basename. Библиотека
`com.github.mwiede:jsch:0.2.26` открывает password-authenticated SSH/SFTP только на одну
операцию. SSH host keys хранятся по TOFU в private `sftp_known_hosts`; изменившийся
ключ отклоняется. Перед upload файл проверяется по SFTP; overwrite требует
подтверждения. После успеха SFTP закрывается и выполняется HTTP Refresh с тем же
путём. Ошибка Refresh после upload показывает отдельный успешный результат Upload.

Activity зарегистрирована как получатель одного `ACTION_SEND` для `text/markdown`,
`text/x-markdown`, `text/plain` и `application/octet-stream`; MIME не считается доверенным,
поэтому display name всегда повторно проверяется как case-insensitive `.md` basename.
Корректный Share переводит в Repository без автозагрузки. `pendingSharedFile` хранит
только URI-строку и display name в `SavedStateHandle`, поэтому переживает recreation,
но не хранится как настройка. Пока он есть, между alias Repository и Menu виден компактный
`Upload →` без имени файла; tap по нему только открывает общее Menu. В Menu показываются
полужирные `Upload here: <name>` и `Cancel shared file`. Индикатор не имеет отдельного UI-состояния:
его видимость напрямую зависит от `pendingSharedFile`, поэтому он сохраняется при навигации/recreation
и исчезает после Upload или Cancel. Пользователь выбирает destination обычной навигацией Repository;
`Upload here` передаёт тот же `UploadSelection` в существующий collision/SFTP/Refresh path.
Pending сохраняется при Cancel Replace или ошибке upload, но очищается сразу
после успешного SFTP, в том числе если последующий Refresh не удался.

Все новые mutation paths строятся только из нормализованных `sftp_root`, текущего
repository-relative path и проверенного basename; separators, `.`/`..` и выход за
root отклоняются до соединения. mkdir/rename/rm/rmdir используют тот же короткий
SFTP lifecycle и после успеха запускают Refresh, сохраняя current path. Ошибка
Refresh не подменяет успешный результат mutation. Комплектный PHP-генератор
включает пустые каталоги первого и второго уровня как directory с `items: []`,
поэтому цепочка New folder → Refresh → открыть папку → Upload работает без
placeholder-файлов.

Ограничения этапа: один репозиторий, нет Sources, repository search, offline cache,
copy/move, recursive delete, multi-select, SFTP key auth и ручной fingerprint
verification. Share поддерживает только один файл; `ACTION_SEND_MULTIPLE` и batch upload нет.

## Web-версия: этапы 1–4B

В `web/` создан минимальный фундамент MDView Web для PHP 8.1+ и обычного shared hosting.
Deployment layout совпадает с архитектурой: `mdview.php` размещается в `repository-root`,
а backend, assets, config templates и dependency — в `mdview-server/`. Реальные репозитории в Git не добавляются.

Структура Web backend:

- `mdview-server/api.php` — единая JSON-точка с оболочками `success/data` и `success/error`;
- `src/Auth/` — `password_verify()`, PHP session, роли `admin`/`user`, grants на repository и `*`,
  server-side read/write checks и session-bound CSRF token;
- `src/Repository/` — discovery пользовательских репозиториев, directory listing и name-only search;
- `src/Reader/` — открытие логического пути через renderer registry и контракт `DocumentView`;
- `src/Renderer/` — общий renderer interface/registry и Markdown renderer;
- `config/*.example.php` — безопасные шаблоны; реальные `app.php`/`users.php` игнорируются Git;
- `assets/` и `mdview.php` — адаптивные HTML/CSS/vanilla-JS Repository и Reader UI.

`repository-root` задаётся явно в ignored `config/app.php` или `MDVIEW_REPOSITORY_ROOT`.
`PathGuard` повторно URL-decode'ит вход, отклоняет absolute paths, `..`, separators/
encoded traversal и после `realpath()` проверяет границу конкретного repository. Внешние symlink не видны
в list/search и не открываются. Reserved `mdview-server` и configured service names не считаются repository
даже для admin. Apache `.htaccess` дополнительно закрывает config/src/dependency от прямого HTTP.

Markdown обрабатывается pinned `erusev/parsedown` 1.8.0 (MIT), vendored одним файлом
без Composer/runtime dependencies. Renderer включает safe + strict mode, проверяет UTF-8,
строит стабильные Unicode heading targets и TOC H1–H3 и возвращает `title/content/toc/metadata`.

Доступны API actions: public `csrf`; CSRF-protected `login`/`logout`; authenticated `session`,
`repositories`, `directory`, `search` и `document`. Мутирующих Repository endpoints на этапе нет,
но `AuthService::requireWrite()`, CSRF и HTTP 409 conflict infrastructure готовы для этапа 5.
Проверки: `php web/tests/run.php`, `php web/tests/http_smoke.php`, PHP lint всех `.php`.

Этап 2 добавил полноценный Repository UI: верхнюю панель с разрешённым backend-ом
выбором репозитория, name-only поиском и заготовкой меню, breadcrumbs логического пути,
touch-friendly список каталогов/файлов и отдельные `⋮` у строк. Каталог и поддерживаемый
документ открываются одиночным click/tap; результаты поиска показывают полный относительный
путь и используют те же переходы. Loading, пустые списки, отсутствие совпадений, потеря
сессии и безопасные API errors имеют отдельные состояния. Интерфейс адаптируется к mobile
без обязательной frontend-сборки и без горизонтальной прокрутки страницы.

`mdview.repository.v1` в `localStorage` хранит выбранный repository, текущий каталог и
scrollTop списка. При reload недоступный repository заменяется первым разрешённым, а
исчезнувший каталог последовательно откатывается к ближайшему существующему родителю.
Перед техническим Reader состояние сохраняется, а Back возвращает тот же DOM списка и
позицию прокрутки. Чистая state/path logic вынесена в `repository-state.js` и проверяется
Node-тестом. ACL в JavaScript не дублируется: список и доступ по-прежнему определяет backend.

Этап 3 добавил renderer-independent Reader UI, использующий только `DocumentView.title` и
`DocumentView.content`. Постоянная верхняя панель имеет финальную трёхчастную структуру
`Contents | Search | Repository`; Repository
возвращает прежний список, каталог и scroll position. При начале загрузки старый документ
очищается и показывается отдельное состояние Opening; 400/403/404/render/server errors
показываются внутри Reader с рабочим возвратом, а 401 переводит к login как потеря сессии.

Reader ограничивает ширину текста на desktop и использует доступную ширину на mobile. Нейтральные
стили покрывают headings, paragraphs, nested lists, strong/emphasis, inline/pre code, blockquotes,
links, rules, tables и images. Длинный code и широкие tables прокручиваются внутри своих блоков,
не создавая горизонтальный scroll страницы. Абсолютные HTTP(S)-ссылки открываются в новой вкладке
с `noopener noreferrer`, внутренние anchors не изменяются. Чистые переходы loading/ready/error/back
вынесены в `reader-state.js` и проверяются без браузера; тип/renderer документа frontend не проверяет.

Этап 4A активировал Contents. Одинаковый для desktop/mobile левый drawer открывается поверх
Reader, имеет собственную вертикальную прокрутку и не меняет layout либо scroll position
документа. Он закрывается повторным Contents, отдельной кнопкой, Escape, кликом по backdrop
или после выбора раздела. Максимальная глубина по умолчанию 3; кнопки `1 / 2 / 3` фильтруют
готовые элементы `DocumentView.toc`, а визуальные отступы различают H1/H2/H3. Переход использует
исключительно `target`, ищет соответствующий `id` только внутри `DocumentView.content` и учитывает
sticky toolbar через `scroll-margin-top`. При пустом TOC Contents disabled. Frontend не анализирует
Markdown/HTML для построения оглавления и не синхронизирует активный пункт при ручной прокрутке.

Этап 4B активировал Search в Reader. Поиск работает регистронезависимо по видимым
текстовым узлам `DocumentView.content`, не обращается к backend и не повторяет Markdown rendering.
Все совпадения временно оборачиваются в `mark`; текущее выделяется отдельно, Previous/Next
цикличны, а счётчик имеет вид `N / total`. Clear и Close полностью удаляют временную
подсветку, не меняя ссылки, HTML-вложенность, heading ids и TOC targets. Search и TOC имеют
независимые UI-state; active-TOC sync и collapsible branches не реализованы.

Позиция чтения каждого документа сохраняется в browser `localStorage` по версионному ключу из
repository id и логического document path. Scroll save debounced с задержкой 200 ms. При повторном
открытии offset восстанавливается один раз и ограничивается текущей высотой страницы.
Явный переход к TOC target или search match имеет приоритет над отложенным restore. Backend и
`DocumentView` не менялись. Upload/New folder/Rename/Move/Delete и активные контекстные
меню остаются для этапа 5.

Hostinger smoke-test выявил и исправил frontend-регрессию login submit: браузер может очистить
`SubmitEvent.currentTarget` после первого `await`. Submit handler синхронно сохраняет ссылку на
форму, а `login-form.js` создаёт из неё `FormData`, после успешной авторизации сбрасывает эту же
форму и больше не читает transient event context. Отдельный Node regression test воспроизводит `currentTarget = null`
во время ожидающего login Promise. Протокол Auth, CSRF и backend API не менялись.

## Текущий статус

Проект подготовлен к первому релизу `0.3.0`.

Основная Python-версия работоспособна и используется как текущая эталонная реализация.

Python-версия имеет три явных режима: `SourcesView`, `RepositoryView`
и `Viewer`. Запуск без аргумента читает XDG-настройки и открывает Sources: слева
системный `Local` и все alias из `repositories[]`, справа — только каталоги
первого уровня выбранного репозитория. Индекс загружается лениво и кэшируется
внутри сеанса по стабильному `RepositorySettings.id`. Активация каталога
открывает существующий Repository View с этим каталогом в качестве начального выбора.

`Enter` и `l` на `Local` используют один action-path: запрашивают путь,
раскрывают `~`, проверяют и читают файл через существующий `read_markdown()`,
затем запускают тот же `Viewer` с возвратом в Sources. Пустой/отменённый ввод и ошибки
чтения оставляют пользователя на `Local`. Прямой `mdview filename.md` не читает настройки,
сразу открывает корневой Viewer и сохраняет прежнее поведение выхода.

Пространственная навигация едина: `h`/← — назад или влево, `l`/→ — вперёд или
вправо, `Tab` — смена панели, `Enter` — активация, `j`/`k` — вертикальный выбор.
В Repository View `h`/← из дерева возвращает в Sources, а из документов — к дереву;
`l`/→ движется вправо или открывает документ. `Esc` либо `h`/← при активной Contents
возвращает из вложенного Reader, `Q` завершает всё приложение.

Клавиша `r` в Repository View повторно вызывает `load_repository()` и заменяет
дерево только после успешной загрузки и валидации нового индекса. Выбранный
каталог восстанавливается по tuple-пути, документ — по относительному `path`;
исчезнувший объект заменяется ближайшим индексом. При ошибке старый индекс и
выбор остаются доступны, а причина показывается в нижней строке.

`/` в Repository View вводит регистронезависимый поиск по полям `name` и
`path` всех документов текущего загруженного индекса, включая корень и
вложенные каталоги. Результаты показываются справа как имя и относительный путь;
`Enter` и контекстный `l` используют обычный `_open_document()`, `Esc` возвращает к
просмотру каталогов. Refresh заменяет источник данных и пересчитывает активные
результаты. Поиск ограничен одним текущим репозиторием и не является полнотекстовым.

`d` в активной правой панели Repository View открывает ввод локального пути с
именем из basename поля `path` по умолчанию. `save_repository_document()` повторно загружает
тот же URL и записывает полученный UTF-8 текст без Markdown-преобразования и автооткрытия.
Запись по умолчанию эксклюзивная; существующий файл заменяется только после
отдельного `y`. Сетевые и `OSError` остаются сообщением в Repository View.

Настройки Python хранятся в `$XDG_CONFIG_HOME/mdview/config.json` или
`~/.config/mdview/config.json`. Модель `Settings` формата 1 содержит `AppSettings` и массив
`RepositorySettings` со стабильным `id`, alias `name`, HTTP(S) `url`, необязательным
`download_dir` и несекретным `AdminSettings`. При первом сетевом запуске автоматически
создаётся временный default с `id=test` и URL `http://ricaro.top/mdrepo/`; локальный Reader
конфиг не читает. Sources показывает все загруженные записи. Локальный
alias имеет приоритет для title, серверное имя остаётся метаданными. Каталог репозитория
имеет приоритет над `app.default_download_dir`; при отсутствии обоих остаётся basename.
Пароль/private key/passphrase/token в JSON отклоняются. Settings UI и SFTP не реализованы.

Контекстные алиасы нормализуются сразу после `get_wch()`: `h` становится
`Esc` только в Contents сетевого Reader, а `l` становится `KEY_ENTER` только
в активном списке документов Repository View. После этого выполняются
существующие action-path возврата и открытия. Regression-тесты проходят через
полные циклы `Viewer.run()`/`RepositoryView.run()`, а не вызывают внутренние
условия алиасов напрямую.

Модель `Repository`, `RepositoryDirectory` и `RepositoryDocument`, разбор и
валидация JSON, построение безопасного URL и UTF-8 HTTP-загрузка отделены от
отрисовки curses. На этом этапе отсутствуют History, файловый менеджер, Settings UI,
добавление/удаление репозиториев из UI, полнотекстовый поиск, постоянное кэширование,
офлайн-режим, массовое/фоновое скачивание, авторизация и SFTP.

В `server/mdrepo/` реализован deploy-комплект динамического format-1 индекса
для Hostinger/shared hosting: `repository.php`, локальный `.htaccess` и
`repository.meta.json`. Источник истины — фактические каталоги и `.md`-файлы в
корне и не более чем на двух уровнях. Пустые каталоги обоих уровней включаются с пустым `items`;
каталог только с файлами не `.md` также остаётся видимым, но сами такие файлы,
symlink и более глубокое содержимое игнорируются. Каталоги и документы стабильно сортируются;
`updated` берётся из максимального mtime метаданных и включённого содержимого.
Ошибки дают HTTP 500 с кратким JSON, подробность остаётся только в server log.
Локальные PHP lint, unit fixture и HTTP smoke-test выполнены. Файлы ещё не
размещены на Hostinger: текущий публичный endpoint остаётся статическим до
ручной загрузки deploy-комплекта и удаления старого `repository.json`.

C-версия собирается и повторяет пользовательский функционал локального
Python Reader: CLI с обязательным файлом, обе панели, оглавление H1–H3, навигацию,
поиск и подсветку, source mapping, resize, минимальный Markdown-рендер,
UTF-8 и восстановление терминала.

Реализованы:

- запуск из командной строки с указанием Markdown-файла;

- запуск без файла в Sources с `Local` и всеми настроенными HTTP-репозиториями;

- TUI на базе `curses`;

- две панели:

  - `Contents`;

  - `Document`;

- оглавление по заголовкам уровней 1–3;

- переключение глубины оглавления клавишами `1`, `2`, `3`;

- навигация по оглавлению;

- переход к выбранному заголовку по `Enter`;

- прокрутка документа;

- переключение панелей по `Tab`; при переходе из оглавления в документ
  выполняется переход к выбранному заголовку;

- Vim-подобная навигация `h/j/k/l`;

- автоматическая синхронизация оглавления с текущим разделом документа;

- корректировка viewport оглавления при смене глубины;

- перенос текста по ширине правой панели;

- связь визуальных строк с исходными строками Markdown;

- перестроение визуальных строк при resize терминала;

- UTF-8, включая русский текст;

  - простые Markdown-таблицы без строки-разделителя и внешних `|`, с выравниванием колонок пробелами;

  - маркированные списки с `-`, отображаемые с маркерами `◆`, `▸`, `▪` по уровням, и нумерованные списки с маркером вида `1.` до трёх уровней вложенности;

  - перенос длинных пунктов с выравниванием продолжения по тексту пункта;

- базовое отображение code blocks;

- поиск по тексту;

- регистронезависимый поиск через `casefold()`;

- поиск по UTF-8 тексту;

- циклический переход между совпадениями;

- поддержка нескольких совпадений в одной исходной строке;

## Управление

Основные клавиши:

- `Tab` — переключить активную панель; при переходе из `Contents` в
  `Document` синхронизировать документ с выбранным заголовком;

- `h` — активировать `Contents`;

- `l` — активировать `Document`; при вызове из `Contents` перейти к
  выбранному заголовку;

- `j` / `k` — перемещение вниз / вверх в активной панели;

- `↑` / `↓` — перемещение в активной панели;

- `PgUp` / `PgDn` — перемещение на страницу;

- `Home` / `End` — начало / конец;

- `Enter` — переход к выбранному заголовку или подтверждение поиска;

- `1` / `2` / `3` — глубина оглавления;

- `/` — ввод поискового запроса;

- `.` — следующее совпадение;

- `,` — предыдущее совпадение;

- `Esc` — отмена ввода поиска или сброс текущего поиска;

- `Q` / `q` — выход.

Стрелки и `Tab` работают наряду с Vim-подобной навигацией.

## Важные технические моменты

### Исходные и визуальные строки

Необходимо различать:

- исходные строки Markdown-файла;

- визуальные строки после переноса по ширине терминала.

Навигация, поиск и переходы по заголовкам не должны зависеть от старых экранных координат.

### Resize

Изменение ширины терминала меняет:

- количество визуальных строк;

- положение перенесённых фрагментов;

- экранные позиции поисковых совпадений.

После resize необходимо перестраивать визуальное представление и восстанавливать логическую позицию по исходным данным.

### Поиск

Поиск выполняется по исходному тексту документа.

Текущее совпадение должно хранить:

- индекс исходной строки;

- точный диапазон символов совпадения.

При отображении нужно корректно переводить диапазон исходного текста в одну или несколько визуальных строк.

### Unicode

Русский текст должен отображаться корректно.

Не следует считать индекс Unicode-символа равным экранной колонке.

Нужно учитывать:

- широкие символы;

- combining characters;

- особенности `casefold()`.

Сложные emoji-графемы и символы неоднозначной ширины могут зависеть от конкретного терминала.

### Терминал

Терминал всегда должен полностью восстанавливаться:

- после обычного выхода;

- после внутренних ошибок;

- после отмены режимов ввода.

## Текущие ограничения

Пока не реализованы:

- полноценный Markdown-рендеринг;

- работа мышью;

- изображения;

- переход по ссылкам;

- несколько одновременно открытых документов;

- Settings UI и выбор активного репозитория;

- темы;

- плагины;

- редактирование.

Длинные строки внутри fenced code blocks сейчас могут обрезаться по ширине панели.

Совпадение поиска, находящееся в обрезанной невидимой части такой строки, нельзя визуально показать.

Выравнивание Markdown-таблиц через `:---`, `---:` и `:---:` и сложная Markdown-разметка внутри ячеек не поддерживаются.

Task lists, смешанные и сложные вложенные списки не поддерживаются.

Python остаётся эталоном. При изменении его пользовательского поведения нужно
одновременно обновлять C-модель, C-TUI и parity-тесты. C-реализация использует
системные wide-character функции текущей UTF-8 locale; редкие Unicode-
преобразования регистра, расширяющиеся в несколько символов, требуют явной
поддержки в C (сейчас покрыт используемый тестами случай `ß` → `ss`/`SS`).

## Принцип развития Markdown-рендера

При улучшении отображения Markdown приоритет:

- универсальность;

- читаемость;

- работа в максимально широком диапазоне терминалов;

- отсутствие обязательной зависимости от цветов;

- отсутствие обязательной зависимости от italic и других необязательных terminal attributes.

Не стремиться сразу реализовать полный стандарт Markdown.
