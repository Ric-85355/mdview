# ANDROID_ARCHITECTURE.md

## Android-версия mdview

### 1. Назначение документа

Этот документ описывает архитектуру и пользовательский интерфейс Android-версии **mdview**.

Android-версия является самостоятельной реализацией общей концепции mdview и не является прямым переносом Python/curses- или C/TUI-кода.

Основные принципы проекта:

- приложение предназначено только для чтения Markdown-файлов;
- редактирование Markdown не поддерживается;
- основным элементом навигации является автоматически построенное оглавление;
- Android-реализация должна сохранять простоту и лёгкость исходного mdview;
- существующие Python- и C-версии не должны изменяться ради Android-порта.

---

## 2. Технологический стек

Предпочтительная реализация:

- язык: **Kotlin**;
- UI: **Jetpack Compose**;
- минимальная версия Android: **Android 9 (API 28)**;
- Android-проект размещается в каталоге:

`android/`

Android-версия должна собираться независимо от Python- и C-версий проекта.

Следует избегать лишних зависимостей. Новая внешняя библиотека должна добавляться только тогда, когда она заметно упрощает реализацию и не создаёт неоправданной сложности.

---

## 3. Общая модель интерфейса

Основной сценарий рассчитан прежде всего на телефон с экраном, вытянутым по вертикали.

В обычном режиме документ занимает почти весь экран.

Интерфейс состоит из:

1. верхней панели управления;
2. области Markdown-документа;
3. раскрывающейся сверху панели оглавления;
4. панели поиска, когда поиск активирован.

Оглавление в обычном режиме скрыто.

---

## 4. Верхняя панель

В верхней части экрана постоянно отображается компактная панель управления.

Она содержит четыре основных элемента.

### 4.1. Главное меню

Кнопка стандартного типа «меню».

Назначение:

- настройки;
- информация «О программе»;
- дополнительные функции, которые могут появиться позднее.

На первом этапе допускается минимальное меню.

---

### 4.2. Глубина оглавления

Отдельная кнопка показывает текущее значение:

- `1`
- `2`
- `3`

Каждый тап циклически меняет режим:

`1 → 2 → 3 → 1`

Значение определяет максимальную глубину заголовков, отображаемых в оглавлении:

- `1` — только `#`;
- `2` — `#` и `##`;
- `3` — `#`, `##` и `###`.

Переключение глубины не должно изменять текущую позицию документа.

---

### 4.3. Показ / скрытие оглавления

Отдельная кнопка переключает состояние оглавления:

- скрыто → показать;
- показано → скрыть.

Кнопка должна работать независимо от жестов.

---

### 4.4. Поиск

Отдельная кнопка открывает режим поиска по текущему документу.

Поиск входит в первую Android-версию.

---

## 5. Оглавление

### 5.1. Формирование

Оглавление автоматически строится по Markdown-заголовкам:

- `#`
- `##`
- `###`

Более глубокие уровни в первой версии не используются.

Иерархия должна визуально отображаться отступами.

---

### 5.2. Расположение

Оглавление раскрывается сверху вниз поверх верхней части области документа.

Оно не открывает отдельный экран.

При открытом оглавлении экран логически делится на две части:

- сверху — оглавление;
- снизу — видимая часть документа.

Оглавление должно занимать разумную часть высоты экрана и оставлять достаточно места для просмотра текста.

Точная доля высоты может быть определена при реализации с учётом размеров экрана.

---

### 5.3. Открытие и закрытие жестами

Оглавление можно открыть жестом сверху вниз.

Оглавление можно закрыть жестом снизу вверх по области самого оглавления.

Кнопка на верхней панели остаётся альтернативным и всегда доступным способом показать или скрыть оглавление.

---

### 5.4. Переход по заголовкам

Тап по тексту пункта оглавления:

1. переводит документ к соответствующему заголовку;
2. не закрывает оглавление;
3. подсвечивает выбранный пункт.

Таким образом пользователь может последовательно переходить между разделами, оставляя оглавление открытым.

Закрытие оглавления является отдельным действием.

---

### 5.5. Синхронизация

При переходе к разделу выбранный пункт оглавления должен быть визуально выделен.

Желательно также поддерживать обратную синхронизацию:

при ручной прокрутке документа приложение определяет текущий раздел и подсвечивает соответствующий пункт оглавления.

Для Android-версии эту функцию следует считать частью целевой архитектуры.

---

## 6. Отображение Markdown

Android-версия должна отображать Markdown как читаемый документ, а не как простой исходный текст.

Минимально должны поддерживаться:

- заголовки;
- обычные абзацы;
- маркированные списки;
- нумерованные списки;
- выделение жирным;
- курсив;
- inline code;
- fenced code blocks;
- ссылки.

Полное покрытие спецификации Markdown не является целью первой версии.

Главный критерий — корректное и удобочитаемое отображение типичной технической документации.

Редактирование Markdown не требуется.

---

## 7. Прокрутка документа

Документ прокручивается обычными Android-жестами.

При переходе из оглавления соответствующий заголовок должен быть расположен как можно ближе к верхней части области документа.

Положение документа не должно неожиданно меняться при:

- открытии оглавления;
- закрытии оглавления;
- изменении глубины оглавления;
- входе и выходе из поиска.

---

## 8. Поиск

Поиск входит в первую Android-версию.

После нажатия кнопки поиска должна появляться строка ввода.

Поиск выполняется по тексту текущего Markdown-документа.

Необходимо предусмотреть:

- ввод поисковой строки;
- отображение количества найденных совпадений;
- переход к следующему совпадению;
- переход к предыдущему совпадению;
- визуальное выделение текущего найденного фрагмента;
- закрытие режима поиска.

При переходе к результату документ автоматически прокручивается к найденному месту.

Поиск не должен изменять исходный файл.

---

## 9. Открытие Markdown-файлов

Необходимо поддержать два основных сценария.

### 9.1. Открытие из mdview

Пользователь запускает приложение и выбирает Markdown-файл через стандартный Android file picker.

Следует использовать стандартные Android-механизмы доступа к документам, без требования полного доступа к файловой системе.

---

### 9.2. «Открыть с помощью»

Android должен позволять открыть `.md`-файл из файлового менеджера или другого приложения через:

**Открыть с помощью → mdview**

Переданный файл становится текущим документом.

---

## 10. Хранение позиции чтения

Приложение должно запоминать позицию чтения отдельно для каждого открывавшегося файла.

При повторном открытии файла приложение восстанавливает последнюю сохранённую позицию.

Для идентификации документа необходимо использовать устойчивый идентификатор, подходящий для Android-механизма доступа к файлам.

Следует учитывать, что путь к файлу не всегда является надёжным или доступным идентификатором.

Хранить нужно только минимально необходимое состояние.

---

## 11. Состояние интерфейса

Для текущего документа приложение должно уметь сохранять или восстанавливать, где это разумно:

- текущую позицию чтения;
- текущий раздел;
- глубину оглавления;
- состояние поиска;
- открыто или закрыто оглавление — если это не ухудшает UX.

Критически важными являются позиция чтения и корректное восстановление документа.

---

## 12. Поворот экрана и изменение конфигурации

При повороте устройства приложение не должно:

- заново открывать файл;
- терять позицию чтения;
- переходить в начало документа;
- терять текущий выбранный раздел.

Состояние должно корректно переживать стандартные изменения конфигурации Android.

---

## 13. Ориентация экрана

Поддерживаются:

- портретная;
- горизонтальная ориентация.

Основной UX проектируется под портретный телефон.

Для первой версии не требуется отдельный сложный планшетный интерфейс.

В дальнейшем на широких экранах допускается двухпанельный режим, аналогичный desktop/TUI-версии:

- оглавление слева;
- документ справа.

Это считается возможным дальнейшим развитием и не является обязательным для первой Android-версии.

---

## 14. Светлая и тёмная тема

Приложение должно поддерживать системную тему Android.

Минимально:

- светлая тема;
- тёмная тема;
- автоматический выбор согласно системным настройкам.

Собственная система цветовых тем в первой версии не требуется.

---

## 15. Архитектурное разделение

Даже если первая реализация компактна, код не должен быть построен как один монолитный экран.

Следует логически разделить как минимум следующие области.

### 15.1. Загрузка документа

Отвечает за:

- получение URI;
- чтение файла;
- обработку ошибок;
- передачу содержимого парсеру.

---

### 15.2. Анализ Markdown

Отвечает за:

- разбор содержимого;
- извлечение заголовков;
- построение структуры оглавления;
- сопоставление заголовков с позициями в документе;
- подготовку данных для отображения.

---

### 15.3. Модель документа

Должна содержать данные, необходимые интерфейсу:

- содержимое документа;
- список заголовков;
- уровни заголовков;
- позиции;
- данные, необходимые для навигации и поиска.

UI не должен повторно разбирать исходный Markdown при каждом действии пользователя.

---

### 15.4. UI

Jetpack Compose отвечает за:

- верхнюю панель;
- область документа;
- панель оглавления;
- поиск;
- отображение текущего состояния;
- обработку пользовательских действий.

---

### 15.5. Состояние просмотра

Отдельный слой должен управлять:

- текущим файлом;
- позицией чтения;
- текущим разделом;
- глубиной оглавления;
- состоянием оглавления;
- поиском.

Предпочтительно использовать стандартный Android-подход с ViewModel и Compose state.

---

### 15.6. Хранение настроек и позиции

Отдельно от UI должно храниться постоянное состояние:

- позиции чтения документов;
- пользовательские настройки;
- другие небольшие параметры приложения.

Не следует использовать полноценную базу данных, если для первой версии достаточно более простого стандартного механизма Android.

---

## 16. Обработка ошибок

Приложение должно корректно обрабатывать:

- файл не существует;
- доступ к файлу потерян;
- файл невозможно прочитать;
- файл пустой;
- ошибка декодирования;
- отсутствие заголовков;
- очень большой документ.

Ошибка чтения файла не должна приводить к аварийному завершению приложения.

Пользователю следует показывать понятное сообщение.

---

## 17. Производительность

Обычные Markdown-документы должны открываться и прокручиваться без заметных задержек.

Следует избегать:

- повторного полного парсинга при каждом recomposition;
- полного перерасчёта оглавления при обычной прокрутке;
- хранения нескольких ненужных копий содержимого документа.

Архитектура должна позволять позднее оптимизировать работу с большими файлами без полного переписывания приложения.

---

## 18. Совместимость с существующим mdview

Android-версия должна сохранять общую концепцию desktop/TUI-версий:

- приложение только для чтения;
- Markdown-файл является основным объектом;
- оглавление строится по заголовкам;
- поддерживаются уровни 1–3;
- переход по заголовку является основным способом навигации;
- интерфейс должен оставаться простым.

При этом Android-версия не обязана имитировать TUI-интерфейс или клавиатурное управление.

---

## 19. Независимость реализаций

Android-проект не должен требовать изменений существующих Python- и C-реализаций.

Общий код между ними не требуется.

Допустимо использовать существующую реализацию только как источник информации о:

- поведении приложения;
- правилах построения оглавления;
- ожидаемой пользовательской логике.

Android-версия должна иметь собственную реализацию, соответствующую возможностям и стандартам Android.

---

## 20. Первая Android-версия

Минимальная первая рабочая версия должна:

1. запускаться на Android 9 и новее;
2. открывать локальный `.md` через системный file picker;
3. принимать `.md` через «Открыть с помощью»;
4. отображать Markdown в читаемом виде;
5. строить оглавление по заголовкам `#`, `##`, `###`;
6. переключать глубину оглавления кнопкой `1/2/3`;
7. открывать и закрывать оглавление кнопкой;
8. поддерживать открытие и закрытие оглавления жестами;
9. переходить по тапу на заголовок без автоматического закрытия оглавления;
10. подсвечивать текущий пункт оглавления;
11. выполнять поиск по документу;
12. переходить к следующему и предыдущему результату поиска;
13. сохранять позицию чтения отдельно для каждого файла;
14. восстанавливать позицию при повторном открытии;
15. сохранять корректное состояние при повороте экрана;
16. поддерживать системную светлую и тёмную тему;
17. не изменять исходный Markdown-файл.

---

## 21. Что не требуется в первой версии

Пока не требуется:

- редактирование Markdown;
- создание файлов;
- работа с несколькими документами одновременно;
- вкладки;
- закладки;
- синхронизация через Интернет;
- облачное хранилище;
- собственный файловый менеджер;
- отображение изображений;
- плагины;
- пользовательские цветовые темы;
- сложный планшетный интерфейс;
- общий программный код с Python- или C-версией.

---

## 22. Развитие архитектуры

В дальнейшем архитектура должна позволять добавить без полной переработки приложения:

- планшетный двухпанельный режим;
- закладки;
- историю последних документов;
- настройку размера текста;
- переход по локальным и внешним ссылкам;
- расширенный Markdown;
- изображения;
- дополнительные настройки отображения.

Эти возможности не должны заранее усложнять первую реализацию.

---

## 23. Фактическая реализация 0.1.0

Первая рабочая версия размещена в `android/` и следует описанному выше
разделению: repository для URI, отдельные Markdown-модель/парсер/поиск,
`ViewerViewModel`, SharedPreferences-хранилище позиций и Compose UI. Парсинг выполняется
при загрузке, а не при recomposition; блоки документа выводятся через `LazyColumn`.

Реализованы file picker, `ACTION_VIEW`, H1–H3 в оглавлении, накладная панель с жестами,
прямая и обратная синхронизация, поиск, позиции по URI, системные темы и все
минимальные Markdown-элементы из раздела 6. URI из picker по возможности получает
persistable read permission; чтение всегда идёт через `ContentResolver`, без требования обычного
файлового пути.

Осознанные ограничения 0.1.0: ссылки имеют визуальный стиль, но не открываются;
таблицы, изображения, полный CommonMark и отдельный планшетный UI не реализованы.

---

## 24. Тестовая нижняя рекламная зона

Для UX-оценки в нижней части главного Android-экрана постоянно выделяется
зона высотой 50 dp и на всю доступную ширину. Она реализована отдельным
Compose-компонентом `AdBannerPlaceholder`. Сейчас он содержит только локальный
нейтральный placeholder. Рекламная сеть, AdMob SDK, рекламные ID, аналитика,
tracking, consent SDK и дополнительные сетевые разрешения не добавлены.

Главный layout измеряет область чтения в оставшейся высоте между верхней панелью и
баннером. Поэтому баннер не накладывается на документ, поиск или оглавление; последний
элемент `LazyColumn` можно довести до конца выделенной области.

Архитектурное правило для возможной будущей рекламы:

- допустим только нижний banner минимальной высоты;
- реклама не накладывается на документ;
- interstitial, fullscreen, popup и вставки между абзацами документа недопустимы.
