# MDView Web — правила доступа и авторизация

## 1. Назначение

Этот документ определяет правила авторизации и доступа пользователей в Web-версии MDView.

Система доступа должна решать две отдельные задачи:

1. определить, **что пользователь имеет право делать**;

2. определить, **к каким репозиториям пользователь имеет доступ**.

Эти два аспекта должны настраиваться независимо друг от друга.

---

## 2. Основная модель доступа

Каждый пользователь имеет:

- уникальное имя пользователя;

- хэш пароля;

- роль;

- список разрешённых репозиториев.

Логическая структура пользователя:

```
User:    username    password_hash    role    repositories
```

Поле `role` определяет набор разрешённых операций.

Поле `repositories` определяет, к каким репозиториям эти операции могут применяться.

---

## 3. Роли

В первой версии должны существовать как минимум две роли:

- `admin`

- `user`

---

## 4. Роль admin

Пользователь с ролью `admin` имеет полный доступ к MDView.

Admin имеет право:

- просматривать все доступные репозитории;

- открывать документы;

- выполнять поиск;

- загружать файлы;

- создавать каталоги;

- переименовывать файлы;

- переименовывать каталоги;

- перемещать файлы;

- перемещать каталоги;

- удалять файлы;

- удалять каталоги;

- выполнять другие операции изменения репозитория, предусмотренные MDView.

По умолчанию для администратора используется:

```
repositories = ["*"]
```

Символ `*` означает доступ ко всем пользовательским репозиториям.

В первой версии не требуется ограничивать администратора отдельным списком репозиториев.

---

## 5. Роль user

Пользователь с ролью `user` имеет доступ только на чтение.

User имеет право:

- видеть разрешённые ему репозитории;

- переходить по каталогам внутри разрешённых репозиториев;

- открывать документы;

- использовать TOC;

- выполнять поиск внутри документа;

- выполнять поиск по именам файлов в разрешённых репозиториях.

User не имеет права:

- загружать файлы;

- создавать каталоги;

- переименовывать файлы;

- переименовывать каталоги;

- перемещать файлы;

- перемещать каталоги;

- удалять файлы;

- удалять каталоги;

- выполнять любые другие операции изменения содержимого репозитория.

Ограничение должно выполняться на сервере, а не только путём скрытия соответствующих элементов интерфейса.

---

## 6. Привязка пользователя к репозиториям

Пользователь может иметь доступ:

- ко всем репозиториям;

- к одному репозиторию;

- к нескольким репозиториям.

Примеры:

```
admin:    role = admin    repositories = ["*"]
```

```
reader1:    role = user    repositories = ["Music", "English"]
```

```
reader2:    role = user    repositories = ["Boats"]
```

```
reader3:    role = user    repositories = ["*"]
```

Последний вариант означает: пользователь может читать все репозитории, но не может их изменять.

---

## 7. Наследование доступа внутри репозитория

Права назначаются на уровне репозитория целиком.

Если пользователь имеет доступ к репозиторию, он получает соответствующие права на:

- корень репозитория;

- все подкаталоги;

- все вложенные подкаталоги;

- все файлы внутри этого репозитория.

Например, если пользователь имеет:

```
repositories = ["Music"]
```

то он имеет доступ ко всему дереву:

```
Music/Music/Reaper/Music/Reaper/Mixing/Music/Reaper/Mixing/document.md
```

Отдельные права на вложенные каталоги в первой версии не поддерживаются.

---

## 8. Отсутствие доступа к репозиторию

Если репозиторий не входит в список разрешённых пользователю, он должен считаться недоступным.

Такой репозиторий:

- не должен отображаться в списке доступных репозиториев;

- не должен появляться в результатах поиска;

- не должен открываться по запросу через MDView API;

- не должен быть доступен через операции Repository subsystem.

Сервер обязан проверять права независимо от того, каким способом был сформирован запрос.

---

## 9. Проверка прав на сервере

Права должны проверяться на каждом серверном запросе, который обращается к репозиторию.

Недостаточно:

- скрывать кнопки в интерфейсе;

- не показывать запрещённые репозитории;

- рассчитывать на корректное поведение Web-клиента.

PHP backend обязан самостоятельно проверить:

1. пользователь авторизован;

2. его сессия действительна;

3. запрошенный репозиторий разрешён этому пользователю;

4. его роль разрешает запрошенную операцию.

Только после этого операция может быть выполнена.

---

## 10. Авторизация пользователя

Web MDView должен иметь собственную форму входа.

Пользователь вводит:

- username;

- password.

Backend проверяет введённые данные.

Пароли в открытом виде хранить запрещено.

На сервере хранится только `password_hash`.

Для проверки пароля следует использовать стандартные механизмы PHP:

- `password_hash()`;

- `password_verify()`.

После успешной авторизации сервер создаёт PHP session.

---

## 11. PHP session

После входа идентификация пользователя выполняется через PHP session.

В сессии должны храниться только данные, необходимые для определения текущего пользователя.

Например:

```
user_idusername
```

Роль и список доступных репозиториев предпочтительно получать из актуальной серверной конфигурации пользователя, а не считать значения из клиента доверенными.

Клиент не должен иметь возможности изменить свою роль или список репозиториев через параметры запроса.

---

## 12. Хранение списка пользователей

В первой версии не требуется база данных.

Список пользователей может храниться в отдельном серверном конфигурационном файле внутри служебной части MDView.

Рекомендуемое расположение:

```
mdview-server/config/users.php
```

или эквивалентная структура.

Файл пользователей:

- не должен быть доступен через Repository UI;

- не должен быть доступен для загрузки через обычный HTTP;

- не должен находиться внутри пользовательского репозитория;

- не должен содержать пароли в открытом виде.

Пример логической структуры:

```
users:    admin:        password_hash        role = admin        repositories = ["*"]    reader1:        password_hash        role = user        repositories = ["Music", "English"]
```

Конкретный PHP-формат хранения определяется при реализации.

---

## 13. Управление пользователями

В первой версии управление пользователями может выполняться вручную через серверный конфигурационный файл.

Отдельный Web-интерфейс управления пользователями не требуется.

В будущем может быть добавлен административный интерфейс для:

- создания пользователя;

- удаления пользователя;

- смены пароля;

- изменения роли;

- изменения списка разрешённых репозиториев.

Это не является обязательной частью первой версии.

---

## 14. Поведение интерфейса в зависимости от роли

Web UI должен адаптироваться к роли пользователя.

Для `admin` должны отображаться элементы управления, связанные с изменением репозитория.

Например:

- Upload;

- New folder;

- Rename;

- Move;

- Delete.

Для `user` эти элементы не должны отображаться или должны быть недоступны.

Однако UI-ограничения являются только удобством интерфейса.

Реальная защита должна выполняться PHP backend.

---

## 15. Поиск

Поиск по Repository выполняется только по именам файлов и каталогов.

Пользователь должен получать результаты только из тех репозиториев, которые ему разрешены.

Для роли `user` поиск является операцией чтения и разрешён.

Полнотекстовый поиск внутри всех документов в Repository в первую версию не входит.

---

## 16. Прямой HTTP-доступ к файлам

Система авторизации MDView действует на операции Web MDView.

Если прямой HTTP-доступ к физическим файлам репозитория остаётся публичным, пользователь потенциально может получить файл напрямую, минуя MDView.

Поэтому необходимо различать:

- доступ через MDView;

- прямой HTTP-доступ к физическому файлу.

В первой версии допускается сохранить существующий прямой HTTP-доступ ради совместимости с текущими клиентами.

При этом следует считать его отдельным каналом доступа, который не контролируется ролями MDView.

В будущем прямой HTTP-доступ может быть закрыт после того, как Android и другие клиенты будут переведены на авторизованный доступ.

---

## 17. Служебные каталоги

Ни один пользователь через Repository subsystem не должен получать доступ к служебным каталогам MDView.

Это относится, как минимум, к:

```
mdview-server/mdview-server/config/
```

Эти каталоги:

- не отображаются как репозитории;

- не участвуют в Repository search;

- не доступны для операций list;

- не доступны для upload;

- не доступны для rename;

- не доступны для move;

- не доступны для delete.

Даже пользователь с ролью `admin` в интерфейсе MDView не должен управлять внутренними файлами самого MDView как обычным репозиторием.

---

## 18. Ошибки доступа

При попытке выполнить запрещённую операцию backend должен вернуть понятную ошибку доступа.

Необходимо различать как минимум:

- пользователь не авторизован;

- сессия недействительна;

- репозиторий недоступен пользователю;

- операция запрещена ролью.

При этом сервер не должен раскрывать внутренние пути файловой системы или другие служебные сведения.

---

## 19. Правила первой версии

В первой версии действует следующая модель:

1. Существуют роли `admin` и `user`.

2. `admin` имеет полный доступ ко всем пользовательским репозиториям.

3. `user` имеет только права чтения.

4. Для каждого `user` задаётся список разрешённых репозиториев.

5. `["*"]` означает доступ ко всем репозиториям.

6. Права на репозиторий автоматически распространяются на всё его содержимое.

7. Отдельные ACL для подкаталогов не используются.

8. Пользователи хранятся в серверной конфигурации.

9. Пароли хранятся только в виде безопасных хэшей.

10. Авторизация выполняется через PHP session.

11. Все права проверяются на сервере.

12. Интерфейс должен скрывать или отключать запрещённые операции, но не заменять этим серверную проверку.

13. Прямой HTTP-доступ к физическим файлам пока может сохраняться отдельно от системы ролей MDView.
