# MDView Web — архитектурные решения

## 1. Назначение архитектуры

Web-версия MDView должна работать с теми же физическими репозиториями документов, что и другие клиенты MDView.

Основной принцип:

- существует один физический набор репозиториев;
- Android MDView работает с этим набором репозиториев;
- Web MDView работает с тем же набором репозиториев;
- будущие клиенты также должны иметь возможность работать с теми же репозиториями;
- отдельная копия репозиториев для Web-версии не создаётся.

Физические файлы являются первичным источником данных.

---

## 2. Корневой каталог repository-root

На сервере существует один корневой каталог `repository-root`.

Он содержит:

1. пользовательские репозитории;
2. служебный каталог Web MDView;
3. входной файл Web-приложения `mdview.php`.

Пример:

```text
repository-root/
    Repository1/
    Repository2/
    Repository3/
    mdview-server/
    mdview.php
```

Каждый пользовательский репозиторий представляет собой обычный каталог первого уровня внутри `repository-root`.

Пример:

```text
repository-root/
    English/
    Boats/
    Music/
    Linux/
```

Каталог `mdview-server` является служебным.

Он:

- не является пользовательским репозиторием;
- не отображается в списке репозиториев;
- не должен быть доступен для пользовательских операций удаления, перемещения или переименования.

Список служебных объектов должен определяться конфигурацией приложения либо явно заданными правилами, а не только предположением, что любой каталог первого уровня является репозиторием.

---

## 3. Точка входа mdview.php

Файл `mdview.php` является единой точкой входа в Web MDView.

При открытии `mdview.php` клиентская часть должна проверить состояние, сохранённое в `localStorage`.

Поведение при запуске:

1. Если сохранён последний открытый документ и этот документ доступен, открыть режим `Document`.
2. Если сохранённого документа нет, открыть режим `Repository`.
3. Если сохранённый документ больше не существует или недоступен, игнорировать это состояние и открыть режим `Repository`.

Файл `mdview.php` не должен содержать всю бизнес-логику приложения.

Он должен выполнять только функции точки входа и подключать необходимые компоненты Web MDView.

---

## 4. Серверная часть MDView

Серверная часть располагается в каталоге:

`mdview-server/`

Backend первой версии реализуется на PHP.

Причина выбора PHP: приложение должно работать на существующем веб-хостинге Hostinger без необходимости запуска отдельного постоянно работающего серверного процесса.

MDView Server должен работать только с заданным `repository-root`.

Основные обязанности MDView Server:

- получить список репозиториев;
- получить содержимое каталога;
- искать файлы в репозитории;
- создавать каталоги;
- загружать файлы;
- переименовывать файлы и каталоги;
- перемещать файлы и каталоги;
- удалять файлы и каталоги;
- определять тип открываемого документа;
- выбирать renderer для документа;
- передавать результат renderer клиентской части.

MDView Server не должен содержать логику отображения конкретного пользовательского интерфейса.

---

## 5. Repository subsystem

Repository subsystem отвечает только за работу с файловой структурой репозиториев.

Repository subsystem не должен заниматься разбором или отображением содержимого документов.

Обязательные операции первой версии:

- `listRepositories` — получить список репозиториев;
- `listDirectory` — получить содержимое каталога;
- `search` — искать файлы внутри выбранного репозитория;
- `createDirectory` — создать каталог;
- `upload` — загрузить файл;
- `rename` — переименовать файл или каталог;
- `move` — переместить файл или каталог;
- `delete` — удалить файл или каталог.

Названия внутренних PHP-функций или API-команд могут отличаться. Здесь указаны логические операции.

Все пути, передаваемые Repository subsystem, должны рассматриваться как пути относительно разрешённого `repository-root`.

Repository subsystem не должен принимать произвольный абсолютный путь файловой системы от клиента.

---

## 6. Reader subsystem

Reader subsystem отвечает за открытие документа.

Последовательность обработки:

1. Получить выбранный файл.
2. Определить тип файла.
3. Найти renderer, зарегистрированный для данного типа.
4. Передать файл renderer.
5. Получить от renderer стандартный объект представления документа.
6. Передать этот объект универсальному Reader UI.

Reader subsystem не должен самостоятельно разбирать Markdown, TXT, RTF, DOCX или другие форматы.

Reader должен работать только со стандартным результатом renderer.

---

## 7. Renderer subsystem

### 7.1. Назначение

Renderer преобразует конкретный формат файла в стандартное внутреннее представление MDView.

Каждый поддерживаемый формат имеет отдельный renderer.

Примеры:

```text
.md   -> MarkdownRenderer
.txt  -> TextRenderer
.rtf  -> RtfRenderer
.docx -> DocxRenderer
```

Для первой версии обязателен только Markdown renderer.

Архитектура должна позволять позднее добавлять новые renderer без изменения Repository subsystem и без создания отдельного Reader UI для каждого формата.

---

## 7.2. Стандартный контракт renderer

Все renderer должны возвращать результат в одном стандартном формате.

Рабочее название этого объекта:

`DocumentView`

Минимальная структура `DocumentView`:

```text
DocumentView:
    title
    content
    toc
    metadata
```

Все четыре поля являются частью общего контракта.

Renderer конкретного типа документа не может заменять эту структуру собственным интерфейсом данных.

---

## 7.3. Поле title

`title` содержит отображаемое название документа.

Renderer самостоятельно определяет источник названия.

Возможные источники:

- заголовок внутри документа;
- свойства документа;
- имя файла.

Если подходящего внутреннего заголовка нет, должно использоваться имя файла.

---

## 7.4. Поле content

`content` содержит подготовленное представление основного содержимого документа.

Для Web MDView основной формат `content` — HTML, пригодный для размещения внутри общего Reader UI.

Renderer отвечает за преобразование своего исходного формата в HTML.

Renderer не должен создавать полную HTML-страницу.

Он не должен формировать:

- основное меню MDView;
- кнопку Repository;
- меню поиска;
- панель TOC;
- общий layout приложения.

Renderer формирует только содержимое документа.

---

## 7.5. Поле toc

`toc` содержит структурированное оглавление документа.

Формат `toc` должен быть одинаковым для всех renderer.

Минимальные свойства элемента TOC:

```text
TOC item:
    level
    title
    target
```

Допускается дополнительная иерархическая структура `children`, если она будет выбрана при реализации.

Смысл полей:

- `level` — уровень заголовка;
- `title` — отображаемый текст;
- `target` — идентификатор точки перехода внутри `content`.

Примеры источников TOC:

- Markdown renderer строит TOC по Markdown-заголовкам;
- DOCX renderer в будущем может строить TOC по стилям заголовков;
- другой renderer использует доступную ему структуру документа.

Если формат документа не имеет структуры, позволяющей построить оглавление, renderer должен вернуть пустой `toc`.

Reader UI при пустом `toc` должен корректно работать без оглавления.

---

## 7.6. Поле metadata

`metadata` содержит дополнительные данные о документе.

Возможные поля:

- исходный тип файла;
- расширение;
- размер файла;
- дата изменения;
- автор;
- кодировка;
- другие доступные свойства.

Набор дополнительных metadata может различаться между форматами.

Отсутствие необязательных metadata не должно препятствовать отображению документа.

При необходимости позднее можно определить обязательную минимальную часть `metadata` отдельным контрактом.

---

## 7.7. Универсальный Reader UI

Reader UI должен работать только с объектом `DocumentView`.

Reader UI не должен проверять:

- является ли документ Markdown;
- является ли документ TXT;
- является ли документ DOCX;
- каким renderer был обработан файл.

Для Reader UI любой успешно обработанный файл является `DocumentView`.

Общая последовательность:

```text
Исходный файл
-> выбор renderer
-> обработка renderer
-> DocumentView
-> Reader UI
```

Таким образом, добавление нового формата документа не должно требовать создания нового пользовательского интерфейса Reader.

---

## 8. Состояние клиента

Состояние Web MDView хранится в браузерном `localStorage`.

Cookies для хранения состояния Reader и Repository не требуются.

В `localStorage` должны или могут храниться:

- последний выбранный репозиторий;
- текущий каталог;
- последний открытый документ;
- позиция чтения документа;
- позиция прокрутки Repository;
- другие параметры интерфейса, если это потребуется.

Позиция чтения сохраняется отдельно для каждого документа.

Документ должен идентифицироваться как минимум сочетанием:

```text
repository + relativePath + filename
```

В первой версии состояние является локальным для конкретного браузера.

Синхронизация состояния между устройствами не требуется.

---

## 9. Прямой HTTP-доступ к файлам

Существующий прямой HTTP-доступ к файлам репозиториев должен быть сохранён.

Наличие MDView Server не означает обязательного запрета обычного HTTP-доступа.

Таким образом, один физический файл может:

- использоваться Android-клиентом;
- открываться напрямую через HTTP;
- открываться через Web MDView.

MDView Server используется для функций, которых недостаточно получить простым HTTP-чтением файла:

- навигация по репозиториям;
- поиск;
- upload;
- создание каталогов;
- rename;
- move;
- delete;
- renderer pipeline.

Политику прямого HTTP-доступа можно изменить позднее, если появятся требования авторизации или разграничения прав.

---

## 10. Безопасность путей

Это обязательное архитектурное требование.

Любая файловая операция MDView Server должна оставаться внутри разрешённого `repository-root`.

Сервер должен предотвращать выход за его пределы через:

- `..`;
- абсолютные пути;
- специально сформированные параметры запроса;
- URL-кодирование специальных последовательностей;
- символьные ссылки, ведущие наружу;
- другие варианты path traversal.

Нельзя считать путь безопасным только потому, что клиентский интерфейс не позволяет ввести произвольный путь.

Проверка должна выполняться на сервере.

Служебные файлы и каталоги приложения должны быть защищены от Repository subsystem независимо от переданных клиентом параметров.

---

## 11. Поддержка новых форматов

Поддержка нового типа документа должна добавляться через renderer.

В типичном случае добавление нового формата должно требовать:

1. создать новый renderer;
2. зарегистрировать расширение или MIME-тип;
3. реализовать преобразование документа в `DocumentView`.

Не должно требоваться:

- менять Repository UI;
- создавать новый режим приложения;
- создавать отдельную систему поиска по интерфейсу;
- создавать отдельную панель TOC;
- переписывать основной Reader UI.

Потенциальные будущие форматы:

- TXT;
- RTF;
- DOCX;
- PDF;
- изображения;
- другие форматы документов.

Поддержка этих форматов не является обязательной для первой версии.

---

## 12. Первая версия

Первая версия Web MDView должна включать:

- PHP backend;
- `mdview.php` как точку входа;
- каталог `mdview-server`;
- работу с единым `repository-root`;
- поддержку нескольких репозиториев;
- режим Repository;
- режим Document;
- Repository subsystem;
- Reader subsystem;
- Renderer subsystem;
- стандартный контракт `DocumentView`;
- Markdown renderer;
- просмотр Markdown;
- TOC;
- поиск внутри открытого документа;
- сохранение состояния через `localStorage`;
- поиск файлов в репозитории;
- upload;
- создание каталога;
- rename;
- move;
- delete;
- сохранение прямого HTTP-доступа к существующим файлам.

---

## 13. Не входит в первую версию

Первая версия не обязана поддерживать:

- синхронизацию позиции чтения между устройствами;
- пользовательские аккаунты;
- несколько уровней прав доступа;
- version history;
- историю изменений;
- совместное редактирование;
- блокировку документов;
- внешние SFTP-репозитории;
- удалённые storage backend;
- renderer для всех возможных типов файлов.

Архитектура не должна намеренно препятствовать добавлению этих возможностей позднее.

---

## 14. Основные архитектурные правила

При реализации необходимо соблюдать следующие правила.

1. Существует один физический `repository-root`.

2. Android MDView, Web MDView и будущие клиенты используют одни и те же физические репозитории.

3. Web MDView не создаёт собственную копию репозитория.

4. Repository subsystem отвечает за файловую структуру, но не за отображение документов.

5. Reader subsystem не знает внутреннее устройство конкретных форматов документов.

6. Каждый формат обрабатывается своим renderer.

7. Все renderer возвращают единый объект `DocumentView`.

8. Reader UI работает с `DocumentView`, а не с исходным типом файла.

9. Серверные файловые операции не могут выходить за пределы `repository-root`.

10. Существующий прямой HTTP-доступ к файлам сохраняется.

11. Добавление нового renderer не должно требовать переработки основного Reader UI.

#### 15. Технологический стек и взаимодействие компонентов

### 15.1 Backend

Серверная часть Web MDView реализуется на PHP.

Причина выбора PHP — размещение приложения на существующем веб-хостинге Hostinger без необходимости запуска отдельного постоянно работающего серверного процесса.

Backend отвечает за:

- работу с репозиториями;

- файловые операции;

- авторизацию и проверку прав;

- поиск по репозиторию;

- выбор renderer;

- обработку документов через renderer;

- формирование данных для Web-клиента.

---

### 15.2 Frontend

Клиентская часть реализуется с использованием:

- HTML;

- CSS;

- vanilla JavaScript.

Использование React, Vue, Angular и других frontend-фреймворков в первой версии не требуется.

Также не должна требоваться обязательная система сборки frontend.

Цель — сохранить приложение максимально простым для размещения, обновления и отладки на обычном веб-хостинге.

---

### 15.3 Взаимодействие frontend и backend

Frontend и backend взаимодействуют через HTTP API.

Для передачи структурированных данных используется JSON.

Frontend не должен получать внутренние пути файловой системы сервера и не должен самостоятельно выполнять файловые операции.

Клиент передаёт серверу только логические идентификаторы и относительные пути внутри разрешённых репозиториев.

Backend выполняет необходимые проверки и возвращает результат операции в JSON.

---

### 15.4 Серверная обработка документов

Обработка исходных документов выполняется на сервере.

Последовательность работы:

1. Web-клиент запрашивает открытие документа.

2. Backend определяет тип файла.

3. Backend выбирает соответствующий renderer.

4. Renderer преобразует исходный файл в стандартный объект `DocumentView`.

5. Backend передаёт `DocumentView` клиенту.

6. Универсальный Reader UI отображает полученный документ.

Frontend не должен содержать отдельные parser-ы для Markdown, TXT, DOCX и других форматов.

Логика конкретного формата должна находиться внутри соответствующего серверного renderer.

---

### 15.5 Формат ответа Reader

Результат обработки документа должен соответствовать стандартному контракту `DocumentView`, определённому в архитектуре MDView.

Минимальный набор данных:

- `title`;

- `content`;

- `toc`;

- `metadata`.

Reader UI должен работать только с этим стандартным представлением и не зависеть от исходного формата документа.

---

### 15.6 Поиск по Repository

Поиск по Repository выполняется на сервере.

В первой версии поиск осуществляется только по:

- именам файлов;

- именам каталогов.

Полнотекстовый поиск по содержимому документов в первую версию не входит.

Поиск должен выполняться только внутри репозиториев, доступных текущему пользователю.

Результаты поиска не должны содержать объекты из репозиториев, к которым пользователь не имеет доступа.

---

### 15.7 Общая структура взаимодействия компонентов

Web-клиент работает в браузере и взаимодействует с PHP backend через HTTP API с передачей данных в JSON.

PHP backend включает следующие логические подсистемы:

- `Repository subsystem` — работа со структурой репозиториев и файловыми операциями;

- `Auth subsystem` — авторизация, сессии и проверка прав доступа;

- `Reader subsystem` — открытие документа и выбор подходящего renderer;

- `Renderer subsystem` — преобразование исходного документа в стандартный `DocumentView`.

Все серверные подсистемы работают с единым физическим `repository-root`.

Пользовательский интерфейс не должен напрямую обращаться к файловой системе сервера.

Общий поток обработки запроса должен быть следующим:

1. Browser UI отправляет HTTP-запрос backend.

2. Backend выполняет авторизацию и проверку прав.

3. Backend передаёт запрос соответствующей подсистеме.

4. Подсистема выполняет операцию с `repository-root`.

5. Backend формирует JSON-ответ.

6. Browser UI обновляет интерфейс на основании полученного ответа.

Для открытия документа дополнительно используется Renderer subsystem, который преобразует исходный файл в стандартный объект `DocumentView`.

---

### 15.8 Общий принцип

Frontend отвечает за интерфейс и взаимодействие с пользователем.

Backend отвечает за данные, права доступа, файловые операции и обработку документов.

Renderer-ы отвечают только за преобразование конкретных форматов документов в стандартный `DocumentView`.

Архитектура первой версии должна сохранять минимальное количество зависимостей и не требовать frontend-фреймворков или отдельной системы сборки. 

#### 16. Дополнительные технические правила первой версии

### 16.1. Единый формат API-ответов

Все HTTP API-методы Web MDView должны возвращать структурированные JSON-ответы в едином формате.

Для успешного запроса ответ должен явно содержать признак успеха и полезные данные.

Для ошибочного запроса ответ должен содержать:

- признак ошибки;

- машинно-читаемый код ошибки;

- человекочитаемое сообщение.

Необходимо различать как минимум следующие ситуации:

- пользователь не авторизован;

- недостаточно прав;

- файл или каталог не найден;

- конфликт имени;

- ошибка загрузки файла;

- неверный запрос;

- внутренняя ошибка сервера.

HTTP status code должен соответствовать смыслу ошибки там, где это возможно.

---

### 16.2. CSRF-защита

Все операции, изменяющие состояние сервера, должны быть защищены от CSRF.

Это относится как минимум к операциям:

- upload;

- createDirectory;

- rename;

- move;

- delete;

- другим будущим операциям изменения данных.

CSRF-защита должна работать совместно с PHP session.

Проверка должна выполняться на сервере.

---

### 16.3. Markdown renderer и внешние зависимости

Для реализации Markdown renderer допускается использование небольшой проверенной PHP-библиотеки.

Не требуется писать собственный полноценный Markdown parser.

Выбранная библиотека должна:

- быть активно поддерживаемой или стабильной;

- иметь понятную лицензию;

- не требовать тяжёлой инфраструктуры;

- подходить для размещения на обычном веб-хостинге;

- позволять получить безопасное HTML-представление Markdown.

Количество внешних зависимостей должно оставаться минимальным.

---

### 16.4. Правила Upload

В первой версии одна операция upload загружает один файл.

Множественная загрузка нескольких файлов одной операцией не требуется.

Если файл с таким именем уже существует в целевом каталоге, сервер не должен молча перезаписывать его.

В такой ситуации backend должен вернуть ошибку конфликта.

Решение о перезаписи, переименовании или отмене должно приниматься явно.

---

### 16.5. Имена файлов и пути

Все пути, передаваемые Web-клиентом, должны быть относительными к соответствующему разрешённому репозиторию.

Клиент не должен передавать абсолютные пути файловой системы сервера.

Система должна корректно поддерживать:

- UTF-8;

- русские имена файлов и каталогов;

- пробелы;

- стандартные символы, допустимые файловой системой и веб-приложением.

Backend обязан выполнять нормализацию и проверку путей до выполнения файловой операции.

---

### 16.6. Назначение HTTP API

HTTP API первой версии является внутренним интерфейсом Web MDView.

Он используется для взаимодействия:

`Web frontend ↔ PHP backend`

На первом этапе API не считается публичным или стабильным интерфейсом для Android MDView и других внешних клиентов.

Текущая Android-версия может продолжать работать существующим способом с тем же физическим `repository-root`.

Перевод Android MDView на единый HTTP API может быть выполнен отдельным этапом в будущем.

Архитектура API при этом не должна намеренно препятствовать такому переходу.
