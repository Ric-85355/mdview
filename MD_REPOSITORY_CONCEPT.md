# Концепция сетевого репозитория Markdown-документов

## 1. Назначение

Проект развивается от простого Markdown-reader'а в сторону лёгкой системы для хранения, поиска и чтения документации.

Основная идея:

> Сетевой репозиторий Markdown-документов с лёгким клиентом для подключения репозиториев, поиска, загрузки и удобного чтения документов с разных устройств.

Система не предназначена для редактирования документов, совместной работы над ними, ведения истории версий или организации сложного документооборота.

Главный принцип:

**простая система для поиска и чтения документов в формате Markdown.**

---

## 2. Основные сценарии использования

### 2.1. Личный репозиторий

Пользователь создаёт документы на разных устройствах или получает их из различных источников, например из ChatGPT.

Готовый Markdown-документ загружается в сетевой репозиторий и после этого доступен с любого устройства, на котором подключён этот репозиторий.

Это позволяет не искать нужную информацию в старых чатах, локальных каталогах или на разных устройствах.

Типичный сценарий:

```text
ChatGPT
   ↓
готовый Markdown-документ
   ↓
репозиторий
   ↓
любое подключённое устройство
   ↓
Reader
```

### 2.2. Рабочий или общий репозиторий

Несколько пользователей могут подключить один репозиторий документации.

После загрузки нового документа он сразу становится доступен всем пользователям, имеющим доступ к этому репозиторию.

Репозиторий находится на сервере и является источником истины.

Локальная копия на конкретном устройстве не является основным хранилищем.

### 2.3. Репозиторий производителя

Производитель оборудования или программного обеспечения может публиковать собственный репозиторий документации.

Например:

```text
Raymarine
  Axiom
    Installation
    Networking
    Troubleshooting
```

Пользователь может:

1. подключить репозиторий производителя;
2. найти нужный документ;
3. открыть его в Reader;
4. при необходимости скачать локальную копию;
5. отключить репозиторий.

Это позволяет получать документацию через единый интерфейс вместо поиска нужных документов на сайтах производителей.

Такие репозитории обычно будут доступны только для чтения.

---

## 3. Два основных режима клиента

### 3.1. Repository View

Предназначен для выбора репозитория, каталога и документа.

Левая панель содержит структуру репозиториев и каталогов.

Правая панель содержит документы выбранного каталога.

Принцип интерфейса:

> слева — навигация по структуре, справа — содержимое выбранного уровня.

Точное поведение интерфейса при одновременном наличии документов и вложенных каталогов будет определено после практического тестирования.

### 3.2. Reader View

После открытия документа программа переходит в уже существующий режим Reader.

Левая панель:

- оглавление документа.

Правая панель:

- текст документа.

Таким образом двухпанельная модель сохраняется во всей программе:

| Режим | Левая панель | Правая панель |
|---|---|---|
| Repository | Репозитории и каталоги | Документы |
| Reader | Оглавление | Текст документа |

---

## 4. Структура репозиториев

К одному клиенту может быть подключено несколько независимых репозиториев.

Например:

```text
Linux
Work
Personal
Raymarine
MikroTik
```

Репозитории можно подключать и отключать.

### 4.1. Глубина каталогов

Внутри репозитория допускается максимум два уровня каталогов.

Таким образом структура левой панели может иметь максимум три уровня:

```text
Repository
  Folder
    Subfolder
```

Документы могут находиться:

```text
Repository → Document

Repository → Folder → Document

Repository → Folder → Subfolder → Document
```

Наличие обоих уровней каталогов не является обязательным.

Пример:

```text
Linux
  README.md

  Network
    nftables.md
    routing.md

    WiFi
      iw.md
      hostapd.md
```

## 5. Функциональность Repository View

### Репозитории

- подключение репозитория;
- отключение репозитория;
- просмотр информации о репозитории;
- обновление состояния репозитория.

### Просмотр

- просмотр структуры каталогов;
- просмотр списка документов;
- открытие документа в Reader;
- просмотр основной информации о документе.

### Поиск

Поиск документов:

- внутри выбранного репозитория;
- потенциально — одновременно во всех подключённых репозиториях.

На данном этапе речь идёт прежде всего о поиске документов, а не о сложном полнотекстовом серверном поиске.

### Локальные документы

- открытие локального Markdown-файла непосредственно в Reader;
- загрузка локального файла в выбранный репозиторий.

### Работа с серверным документом

- открытие документа;
- загрузка его локальной копии;
- удаление документа при наличии административных прав.

### Каталоги

При наличии административных прав:

- выбор каталога назначения при загрузке;
- создание каталога;
- удаление каталога.

---

## 6. Что сознательно не входит в систему

Система должна оставаться простой.

На данном этапе не предусматриваются:

- встроенный Markdown-редактор;
- совместное редактирование;
- комментарии;
- история изменений;
- версии документов;
- сложная система документооборота;
- автоматическая синхронизация локальных каталогов;
- конфликт-менеджмент;
- сложное управление правами внутри самого клиента.

Это не аналог SharePoint, Google Docs или Git.

---

## 7. Сетевая модель

Репозиторий физически расположен на сервере.

Он представляет собой обычную файловую структуру:

```text
repository/
    linux.md

    network/
        nftables.md
        routing.md

        wifi/
            iw.md
            hostapd.md
```

Основным содержимым репозитория являются Markdown-файлы.

---

## 8. HTTP/HTTPS как протокол чтения

Репозиторий одновременно является обычным веб-ресурсом.

Документы доступны по HTTP/HTTPS.

Например:

```text
https://docs.example.com/network/nftables.md
```

Это позволяет использовать один и тот же репозиторий двумя способами:

```text
специализированный клиент
        ↓
Repository View → Reader
```

или:

```text
обычный браузер
        ↓
URL документа
```

Специальный клиент не является обязательным условием доступа к документации.

---

## 9. Размещение репозитория на существующем сайте

Репозиторий не обязан находиться в корне отдельного сайта или домена.

Он может размещаться в любом доступном подкаталоге существующего веб-сайта, в том числе сайта на WordPress.

Например:

```text
https://example.com/mdrepo/
```

В этом случае именно этот URL считается корневым адресом репозитория.

Клиент формирует адрес служебного индекса относительно корня репозитория:

```text
https://example.com/mdrepo/repository.json
```

Документы также располагаются относительно этого корня:

```text
https://example.com/mdrepo/linux/network.md
https://example.com/mdrepo/hardware/mikrotik.md
```

Физически структура на сервере может выглядеть так:

```text
public_html/
├── файлы существующего сайта
└── mdrepo/
    ├── repository.meta.json
    ├── repository.php
    ├── linux/
    │   ├── network.md
    │   └── samba.md
    └── hardware/
        └── mikrotik.md
```

`repository.json` может не существовать как физический файл.

Запрос:

```text
GET /mdrepo/repository.json
```

может перенаправляться веб-сервером на небольшой серверный скрипт, например `repository.php`, который:

1. определяет каталог текущего репозитория;
2. обходит только его содержимое;
3. учитывает допустимую глубину каталогов;
4. читает `repository.meta.json`;
5. формирует актуальный `repository.json`;
6. возвращает его клиенту с типом `application/json`.

Таким образом на одном сайте при необходимости может существовать несколько независимых репозиториев:

```text
https://example.com/docs-personal/
https://example.com/docs-work/
https://example.com/docs-public/
```

Каждый из них имеет собственный корень, метаданные и структуру документов.

### Принцип адресации

Клиенту не важно, где физически расположен репозиторий и является ли сайт выделенным сервером документации.

Для клиента репозиторий определяется единственным параметром:

```text
Repository URL
```

например:

```text
https://example.com/mdrepo/
```

Все остальные адреса вычисляются относительно него.

## 10. repository.json

Для получения структуры репозитория клиент использует:

```text
repository.json
```

Например:

```text
https://docs.example.com/repository.json
```

Рабочая версия формата:

```json
{
  "format": 1,
  "name": "Linux Documentation",
  "description": "Personal Linux documentation repository",
  "updated": "2026-08-30T09:30:00Z",

  "capabilities": {
    "upload": true,
    "delete": true,
    "mkdir": true
  },

  "items": [
    {
      "type": "directory",
      "name": "Network",
      "items": [
        {
          "type": "document",
          "name": "nftables",
          "path": "network/nftables.md",
          "updated": "2026-08-28T14:20:00Z",
          "size": 18420
        }
      ]
    }
  ]
}
```

### 10.1. Основные поля

#### format

Версия формата описания репозитория.

Нужна для возможности дальнейшего развития протокола без нарушения совместимости со старыми клиентами.

#### name

Отображаемое название репозитория.

#### description

Необязательное описание.

#### updated

Дата последнего изменения репозитория.

#### capabilities

Описание поддерживаемых операций.

Например:

```json
"capabilities": {
  "upload": true,
  "delete": true,
  "mkdir": true
}
```

Для публичного репозитория производителя:

```json
"capabilities": {
  "upload": false,
  "delete": false,
  "mkdir": false
}
```

#### items

Структура каталогов и документов.

Для документа используется относительный путь:

```json
"path": "network/nftables.md"
```

Если индекс находится по адресу:

```text
https://docs.example.com/repository.json
```

то документ будет доступен по адресу:

```text
https://docs.example.com/network/nftables.md
```

Полный URL внутри индекса хранить не требуется.

Это позволяет перенести репозиторий на другой сервер или домен без изменения его внутренней структуры.

## 11. repository.json генерируется автоматически

`repository.json` не должен вручную поддерживаться пользователем и не должен редактироваться клиентом.

Источником истины является файловая структура репозитория на сервере.

При запросе:

```text
GET /repository.json
```

сервер формирует индекс на основании фактического содержимого каталогов.

Таким образом:

```text
файловая структура
        ↓
генератор индекса
        ↓
repository.json
        ↓
клиент
```

Это даёт несколько важных преимуществ:

- индекс не расходится с реальным содержимым;
- загрузка файла автоматически отражается в репозитории;
- удаление файла автоматически отражается в репозитории;
- создание каталога автоматически отражается в репозитории;
- файлы можно помещать в репозиторий сторонними средствами;
- клиенту не требуется отдельно обновлять индекс после каждого изменения.

---

## 12. Метаданные самого репозитория

Данные, которые невозможно получить непосредственно из структуры каталогов, могут храниться в небольшом служебном файле.

Например:

```text
repository.meta.json
```

Он может содержать:

```json
{
  "name": "Linux Documentation",
  "description": "Personal Linux documentation repository"
}
```

Генератор `repository.json` объединяет эти метаданные с фактической файловой структурой.

### Фактическая реализация тестового сервера

Deploy-комплект находится в `server/mdrepo/`. Локальный `.htaccess` направляет
только запрос `repository.json` в `repository.php`; обычные `.md` продолжают
обслуживаться как статические файлы. Скрипт не принимает пользовательские пути,
не следует по symlink и использует каталог самого скрипта как корень.

Индексируются документы в корне, каталоге и подкаталоге второго уровня.
Более глубокие каталоги, файлы не `.md` и каталоги без индексируемых документов
не попадают в `items`. Сначала регистронезависимо сортируются каталоги, затем
документы. `updated` — максимальное время изменения метаданных, включённых
Markdown-файлов и включённых каталогов, представленное в ISO 8601 UTC.

`description` остаётся необязательным. Отсутствующий или пустой `name`,
отсутствующий/повреждённый `repository.meta.json` и ошибки сканирования приводят
к HTTP 500 с кратким JSON без stack trace и серверных путей.

## 13. Пользователи и права доступа

Система не реализует сложную собственную модель пользователей и прав.

Используются только две роли:

### user

Обычный пользователь работает с репозиторием по HTTP/HTTPS.

Доступные действия:

- подключить репозиторий;
- получить `repository.json`;
- просматривать структуру каталогов;
- искать документы;
- открывать документы в Reader;
- скачивать документы локально.

Для обычного пользователя SFTP-доступ не требуется.

Если репозиторий публичный, отдельная авторизация пользователя может вообще отсутствовать.

### admin

Администратор имеет все возможности обычного пользователя и дополнительно получает доступ к файловой структуре репозитория по SFTP.

Доступные административные действия:

- загрузка новых Markdown-документов;
- удаление документов;
- создание каталогов;
- удаление каталогов;
- при необходимости перемещение или переименование файлов средствами файлового доступа.

После изменения файловой структуры сервер автоматически формирует новое состояние `repository.json`, поэтому отдельная операция обновления индекса не требуется.

---

## 14. Разделение протоколов

Права естественно разделяются по способу доступа:

```text
user
  ↓
HTTP/HTTPS
  ↓
read / search / open / download
```

```text
admin
  ↓
HTTP/HTTPS + SFTP
  ↓
read + upload / delete / mkdir
```

Клиент не должен самостоятельно управлять сложными ACL, правами отдельных каталогов или правами на отдельные документы.

Права записи определяются настройками SFTP-сервера и файловой системы сервера.

---

## 15. Публичные репозитории

Для публичных репозиториев, например документации производителя, схема может быть максимально простой:

```text
HTTP/HTTPS — доступен всем
SFTP — доступен только владельцу репозитория
```

Пользователь может подключить такой репозиторий, читать и скачивать документы, но не изменять его содержимое.

---

## 16. Частные репозитории

Если требуется ограничить чтение репозитория, авторизация HTTP/HTTPS может обеспечиваться средствами самого веб-сервера или хостинга.

Это не меняет модель ролей:

- `user` — чтение;
- `admin` — чтение и полный административный доступ.

Учётные данные, пароли, ключи и другие секреты не хранятся в `repository.json`.

---

## 17. Загрузка и изменение репозитория

Для чтения используется HTTP/HTTPS.

Для операций записи используется SFTP.

Таким образом:

```text
HTTP/HTTPS
    ↓
чтение индекса
чтение документов
скачивание
```

и:

```text
SFTP
    ↓
upload
delete
mkdir
```

Это позволяет не создавать собственный API для базовых файловых операций.

При возможности административный файловый доступ желательно ограничивать только каталогом конкретного репозитория, а не всем сайтом.

---

## 18. Серверная архитектура

Основная идея серверной реализации:

> Репозиторий остаётся обычным каталогом на сервере, а специальная логика сведена практически к одному генератору индекса.

Минимальный сервер может состоять из:

```text
Web server
    +
SFTP server
    +
Repository index generator
    +
Filesystem
```

Например:

```text
/srv/docs/linux/
    repository.meta.json
    network/
        nftables.md
        routing.md
```

Web-сервер предоставляет:

```text
https://docs.example.com/linux/...
```

SFTP предоставляет тот же каталог администратору для операций записи.

---

## 19. Связь с существующим Reader

Repository View не заменяет существующий Markdown Reader.

Он является дополнительным уровнем навигации перед ним.

Общая схема программы:

```text
             ┌───────────────┐
             │ Repository    │
             │ View          │
             └───────┬───────┘
                     │
                     │ открыть документ
                     ↓
             ┌───────────────┐
             │ Reader        │
             │ TOC + Text    │
             └───────────────┘
```

Также Reader может запускаться непосредственно:

```text
Local Markdown file
        ↓
Reader
```

После чего локальный документ при необходимости может быть загружен в один из подключённых репозиториев.

## 20. Предлагаемый порядок разработки

Разработку целесообразно вести поэтапно.

### Этап 1. Repository View только для чтения

- подключение одного репозитория по URL;
- загрузка `repository.json`;
- отображение дерева каталогов;
- отображение списка документов;
- открытие документа по HTTP в существующем Reader.

### Этап 2. Серверная генерация repository.json

- простой генератор;
- обход каталога;
- поддержка `repository.meta.json`;
- динамическая выдача индекса по HTTP.

### Этап 3. Поиск

- поиск по текущему репозиторию;
- затем поиск по всем подключённым репозиториям.

На первом этапе поиск выполняется по названиям и путям документов.

### Этап 4. Локальные файлы

- открытие локального `.md`;
- скачивание документа из репозитория локально.

### Этап 5. Admin-функции

- настройка SFTP;
- загрузка локального файла;
- выбор каталога назначения;
- создание каталога;
- удаление документа и каталога.

### Этап 6. Несколько репозиториев

- постоянный список подключённых репозиториев;
- подключение и отключение;
- хранение настроек;
- отдельные параметры доступа для каждого репозитория.

При этом архитектура клиента с самого начала не должна предполагать, что репозиторий может быть только один.

---

## 21. Главный принцип проекта

Проект должен оставаться небольшим и понятным.

Репозиторий — это не специальная база данных и не сложная серверная система.

Это:

```text
обычный каталог
+
Markdown-файлы
+
HTTP/HTTPS
+
SFTP
+
автоматически сформированный индекс
```

А клиент предоставляет удобный единый интерфейс:

```text
подключить
→ найти
→ открыть
→ прочитать
```

и, для администратора:

```text
открыть локальный документ
→ загрузить в репозиторий
→ документ сразу доступен остальным пользователям
```

Именно простота этой модели является одним из основных требований проекта.
