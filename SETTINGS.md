# Унифицированная модель настроек mdview

## 1. Назначение

Настройки `mdview` должны быть спроектированы так, чтобы одна и та же логическая модель использовалась:

- в Python/TUI-версии;

- в Android-версии;

- в возможных будущих клиентах.

При этом способ физического хранения настроек на разных платформах может отличаться.

Главный принцип:

> одинаковая модель данных — платформенное хранение.

---

# 2. Уровни настроек

Настройки делятся на два уровня:

1. общие настройки приложения;

2. настройки конкретного репозитория.

---

# 3. Общие настройки приложения

Общие настройки относятся ко всему клиенту независимо от подключённого репозитория.

На первом этапе необходима настройка:

```text
default_download_dir
```

Она определяет каталог по умолчанию для сохранения локальных копий документов.

В дальнейшем сюда могут добавляться другие общие параметры приложения.

Например:

```text
AppSettings
    default_download_dir
```

Не следует заранее добавлять параметры, которые пока не нужны.

---

# 4. Настройки репозитория

Каждый подключённый репозиторий имеет собственный набор настроек.

Минимальная модель:

```text
RepositorySettings
    id
    name
    url
    download_dir

    admin
        enabled
        sftp_host
        sftp_port
        sftp_user
        sftp_root
        auth_method
```

---

# 5. Идентификатор репозитория

Каждый репозиторий должен иметь стабильный внутренний идентификатор:

```text
id
```

Например:

```text
personal
linux-docs
raymarine
```

`id` не должен зависеть от отображаемого имени репозитория.

Это позволяет изменить:

- `name`;

- URL;

- другие параметры;

не создавая для клиента новый репозиторий.

`id` используется только внутри клиента и не обязан совпадать с данными серверного `repository.json`.

---

# 6. Имя репозитория

Поле:

```text
name
```

содержит отображаемое имя репозитория в клиенте.

Например:

```text
Personal
Linux Documentation
Raymarine
```

В дальнейшем возможно использование имени, полученного из `repository.json`, но локальная модель должна допускать собственное отображаемое имя.

---

# 7. URL репозитория

Поле:

```text
url
```

содержит корневой HTTP/HTTPS URL репозитория.

Например:

```text
https://example.com/mdrepo/
```

От него клиент получает:

```text
repository.json
```

и строит URL документов.

---

# 8. Каталог локального сохранения

Для каждого репозитория может быть задан собственный:

```text
download_dir
```

Например:

```text
Linux Documentation
    download_dir = ~/Documents/Linux
```

или:

```text
Raymarine
    download_dir = ~/Documents/Raymarine
```

Поле необязательное.

Если оно не задано, используется:

```text
AppSettings.default_download_dir
```

Таким образом действует правило:

```text
repository.download_dir
        ↓
если задан — использовать его
        ↓
иначе
        ↓
global.default_download_dir
```

---

# 9. Платформенные особенности пути

`download_dir` является логической настройкой, но путь может иметь разный вид на разных платформах.

Python/Linux:

```text
/home/user/Documents/mdview
```

Android:

путь или идентификатор каталога, допустимый для Android storage model.

Поэтому клиенты не должны исходить из того, что значение пути обязательно является POSIX-путём.

Общая модель должна описывать назначение настройки, а не конкретную реализацию файловой системы.

---

# 10. Admin-настройки

Административные параметры относятся только к репозиторию, где пользователь имеет право изменения файлов.

Пример:

```text
admin.enabled
admin.sftp_host
admin.sftp_port
admin.sftp_user
admin.sftp_root
admin.auth_method
```

---

# 11. admin.enabled

Поле:

```text
enabled
```

показывает, настроен ли для данного клиента административный доступ к репозиторию.

Например:

```text
false
```

для обычного публичного репозитория производителя.

И:

```text
true
```

для собственного репозитория пользователя.

---

# 12. SFTP host

Поле:

```text
sftp_host
```

содержит адрес SFTP-сервера.

Он не обязан совпадать с HTTP-хостом репозитория.

Например:

```text
Repository URL:
https://example.com/mdrepo/

SFTP host:
srv123.hosting-provider.com
```

---

# 13. SFTP port

Поле:

```text
sftp_port
```

содержит порт SFTP.

Значение не должно быть жёстко задано как `22`, так как некоторые хостинги используют другой порт.

---

# 14. SFTP user

Поле:

```text
sftp_user
```

содержит имя пользователя для административного SFTP-доступа.

---

# 15. SFTP root

Поле:

```text
sftp_root
```

указывает путь к корню данного репозитория с точки зрения SFTP.

Например:

```text
/public_html/mdrepo
```

HTTP URL и SFTP path рассматриваются как независимые параметры.

Например:

```text
HTTP:
https://example.com/mdrepo/linux/network.md

SFTP:
 /public_html/mdrepo/linux/network.md
```

---

# 16. Способ авторизации

Поле:

```text
auth_method
```

определяет способ SFTP-авторизации.

Первоначально достаточно предусмотреть:

```text
password
key
```

Реализация конкретных методов может добавляться по мере необходимости.

---

# 17. Секретные данные

Пароли, приватные ключи и другие секреты не должны храниться непосредственно в общем конфигурационном файле.

Общий конфиг содержит только:

- адреса;

- имена пользователей;

- способ авторизации;

- ссылки или идентификаторы на защищённое хранилище, если это потребуется.

Фактические секреты должны храниться платформенным способом.

---

# 18. Хранение секретов в Python/Linux

Для Python/Linux в дальнейшем желательно использовать системное защищённое хранилище, например keyring.

До реализации безопасного хранения допускается:

- запрос пароля при выполнении административной операции;

- использование заранее настроенного SSH-ключа пользователя.

Не следует сохранять пароль открытым текстом в `config.json`.

---

# 19. Хранение секретов в Android

Android-клиент должен использовать защищённое системное хранилище.

Для секретов следует использовать Android Keystore или соответствующий безопасный механизм.

Обычные настройки репозитория могут храниться отдельно от секретов.

---

# 20. Физическое хранение настроек

## Python/TUI

Предлагаемое расположение:

```text
~/.config/mdview/config.json
```

или другой путь в соответствии с XDG conventions.

## Android

Физическое хранение может быть реализовано через:

```text
DataStore
```

или другой штатный механизм Android.

Android не обязан физически использовать JSON-файл.

Важно только, чтобы логическая структура данных соответствовала общей модели.

---

# 21. Пример логической конфигурации

Пример в JSON-представлении:

```json
{
  "format": 1,

  "app": {
    "default_download_dir": "/home/user/Documents/mdview"
  },

  "repositories": [
    {
      "id": "personal",
      "name": "Personal",
      "url": "https://example.com/mdrepo/",
      "download_dir": "/home/user/Documents/Personal",

      "admin": {
        "enabled": true,
        "sftp_host": "server.example.com",
        "sftp_port": 22,
        "sftp_user": "roman",
        "sftp_root": "/public_html/mdrepo",
        "auth_method": "key"
      }
    },

    {
      "id": "raymarine",
      "name": "Raymarine",
      "url": "https://docs.example.com/raymarine/",
      "download_dir": null,

      "admin": {
        "enabled": false
      }
    }
  ]
}
```

Это пример логической структуры, а не обязательное физическое представление для всех платформ.

---

# 22. Версия формата

Конфигурационная модель должна иметь:

```text
format
```

Например:

```text
format = 1
```

Это позволит позже расширять структуру настроек с сохранением совместимости.

---

# 23. Несколько репозиториев

Хотя текущая Python-версия может пока работать только с одним репозиторием, модель настроек сразу должна поддерживать:

```text
repositories[]
```

То есть несколько независимых подключённых репозиториев.

Не следует проектировать конфиг вокруг единственного:

```text
repository_url
```

верхнего уровня.

---

# 24. Независимость платформ

Python- и Android-клиенты должны одинаково понимать следующие понятия:

```text
AppSettings

RepositorySettings

Repository ID

Repository URL

Download location

Admin access

SFTP connection

Authentication method
```

Но они могут по-разному реализовывать:

- выбор каталога;

- файловые пути;

- хранение конфигурации;

- хранение секретов;

- сетевые библиотеки;

- пользовательский интерфейс.

---

# 25. Главный принцип

Настройки должны описывать не конкретную реализацию Python-клиента, а сущности самого `mdview`.

То есть модель должна отвечать на вопросы:

```text
Какие репозитории подключены?

Где находится репозиторий?

Куда сохранять его документы?

Есть ли административный доступ?

Как подключиться по SFTP?
```

А уже конкретный клиент решает, как эти данные физически хранить и каким интерфейсом их редактировать.
