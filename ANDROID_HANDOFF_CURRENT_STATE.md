# mdview — промежуточный срез проекта и задача для Android-версии

## 1. Назначение документа

Этот документ фиксирует текущее состояние проекта `mdview` и определяет промежуточную Android-версию, которую нужно реализовать сейчас.

Цель Android-этапа — не догнать Python-версию по всем функциям, а получить уже полезный мобильный клиент для реального использования:

- просматривать документы из сетевого Markdown-репозитория;
- читать их в существующем Android Reader;
- загружать локальные `.md`-файлы со смартфона в репозиторий.

После этого основная разработка Python-версии может продолжаться отдельно.

---

## 2. Общая концепция mdview

`mdview` развивается из простого Markdown-reader'а в лёгкую систему для хранения, поиска и чтения Markdown-документации.

Основная модель:

```text
сетевой репозиторий
        ↓
каталоги
        ↓
Markdown-документы
        ↓
Reader
```

Репозиторий является обычным каталогом на веб-сервере.

Для чтения используется HTTP/HTTPS.

Для административных операций записи планируется SFTP.

Система должна оставаться простой и не превращаться в SharePoint, Git или полноценную систему документооборота.

---

## 3. Серверная модель репозитория

Тестовый репозиторий:

```text
http://ricaro.top/mdrepo/
```

Индекс:

```text
http://ricaro.top/mdrepo/repository.json
```

`repository.json` формируется сервером автоматически на основании фактической структуры каталогов и `.md`-файлов.

Источником истины является файловая структура репозитория.

В индекс включаются только:

```text
*.md
```

Файлы других типов игнорируются.

Это позволяет использовать в качестве репозитория даже каталог, где одновременно находятся исходный код, изображения, конфигурационные файлы, архивы и другие данные.

`mdview` видит только Markdown-документы.

---

## 4. Допустимая структура репозитория

Внутри репозитория допускается максимум два уровня каталогов:

```text
Repository
  Folder
    Subfolder
```

Документы могут находиться:

```text
Repository → Document
Repository → Folder → Document
Repository → Folder → Subfolder → Document
```

---

## 5. Основные роли

Система использует простую модель из двух ролей.

### user

Работает по HTTP/HTTPS.

Может:

- подключить репозиторий;
- получить `repository.json`;
- просматривать структуру;
- искать документы;
- открывать документы;
- скачивать локальные копии.

SFTP обычному пользователю не нужен.

### admin

Имеет все возможности `user` и дополнительно доступ к репозиторию по SFTP.

Может:

- загружать документы;
- удалять документы;
- создавать каталоги;
- удалять каталоги;
- выполнять другие файловые операции в пределах разрешённого SFTP-доступа.

Сложная ACL-модель внутри `mdview` не используется.

---

## 6. Текущая модель настроек

Настройки унифицированы концептуально для Python и будущего Android-клиента.

Основные сущности:

```text
Settings
AppSettings
RepositorySettings
AdminSettings
```

Для репозитория предусмотрены:

```text
id
name
url
download_dir

admin:
    enabled
    sftp_host
    sftp_port
    sftp_user
    sftp_root
    auth_method
```

Секреты — пароль, passphrase, приватные ключи, токены — не должны храниться в обычном конфигурационном JSON.

Для Android секреты должны храниться безопасным платформенным способом.

---

## 7. Текущее состояние Python-версии

Python/TUI-версия уже реализует значительную часть концепции.

### Reader

Работает существующий Markdown Reader:

- двухпанельный TUI;
- содержание слева;
- текст справа;
- Markdown-rendering;
- поиск;
- Vim-подобная навигация;
- UTF-8;
- возврат между режимами.

### Repository View

Реализовано:

- чтение сетевого `repository.json`;
- отображение каталогов;
- отображение документов;
- открытие удалённого документа в существующем Reader;
- возврат из Reader;
- Refresh / повторная загрузка индекса;
- поиск по репозиторию;
- локальное сохранение удалённого документа.

### Search

Поиск текущего репозитория работает по:

- имени документа;
- относительному пути.

Полнотекстовый серверный поиск пока не реализован.

### Settings

Реализована система настроек.

Конфигурация хранится:

```text
$XDG_CONFIG_HOME/mdview/config.json
```

если `XDG_CONFIG_HOME` задан, иначе:

```text
~/.config/mdview/config.json
```

Модель уже поддерживает:

```text
repositories[]
```

то есть несколько репозиториев.

### Sources View

В Python-версии реализован верхний режим Sources.

Левая панель:

```text
Local
+ все репозитории из repositories[]
```

Правая панель:

- для выбранного репозитория — каталоги первого уровня.

`Local` позволяет открыть локальный Markdown-файл путём ручного ввода пути.

---

## 8. Три режима интерфейса

Зафиксирована следующая модель.

### Режим 1 — Sources

Слева:

```text
Local
Repository 1
Repository 2
...
```

Справа:

```text
каталоги первого уровня выбранного репозитория
```

### Режим 2 — Repository

Слева:

```text
дерево каталогов конкретного репозитория
```

Справа:

```text
документы выбранного каталога
```

### Режим 3 — Reader

Слева:

```text
содержание документа
```

Справа:

```text
текст документа
```

Общий принцип интерфейса:

> слева — структура и навигация, справа — содержимое выбранного объекта.

---

## 9. Зафиксированная навигация Python/TUI

Используется единая пространственная модель:

```text
h / ←   назад или влево
l / →   вперёд или вправо
Tab     смена панели
Enter   активировать выбранный объект
j / ↓   вниз
k / ↑   вверх
```

Эта модель является концептуальной частью интерфейса, но Android не обязан буквально воспроизводить клавиатурные команды.

---

## 10. Почему Android-версия нужна уже сейчас

Android-клиент требуется для реального ежедневного сценария.

Типичная ситуация:

```text
ChatGPT на смартфоне
        ↓
обсуждение
        ↓
готовый Markdown-файл
        ↓
файл сохраняется на телефон
        ↓
mdview
        ↓
Upload в личный репозиторий
        ↓
документ сразу доступен с других устройств
```

Поэтому ждать полного завершения Python-версии не требуется.

Архитектурная основа уже достаточно стабильна:

- формат репозитория определён;
- `repository.json` работает;
- HTTP-чтение проверено;
- структура Repository View проверена;
- модель настроек определена;
- SFTP выбран как способ административной записи.

---

## 11. Цель промежуточной Android-версии

Сейчас необходимо сделать минимальную, но реально полезную Android-версию.

Она должна уметь:

1. подключаться к тестовому репозиторию;
2. загружать `repository.json`;
3. показывать каталоги и документы;
4. открывать документ в существующем Android Reader;
5. обновлять содержимое репозитория;
6. выбирать локальный `.md` на телефоне;
7. загружать выбранный файл в репозиторий по SFTP;
8. после загрузки обновлять `repository.json`, чтобы новый документ сразу появился в интерфейсе.

---

## 12. Что уже есть в Android-проекте

Android-версия `mdview` уже существовала до Repository-функционала.

В ней уже были реализованы:

- Kotlin + Compose;
- открытие локальных файлов;
- Android file picker / `content://`;
- Markdown Reader;
- заголовки;
- списки;
- bold/italic;
- inline code;
- code blocks;
- ссылки;
- содержание;
- поиск;
- сохранение позиции;
- работа с поворотом экрана;
- light/dark;
- обработка ошибок.

Новый Repository-функционал должен использовать существующий Reader, а не создавать отдельный renderer.

---

## 13. Промежуточный Android Repository View

Для первого мобильного этапа допустимо работать только с одним репозиторием.

Тестовый URL:

```text
http://ricaro.top/mdrepo/
```

Не требуется сразу переносить полный Python Sources View с несколькими репозиториями.

Главная цель — быстро получить рабочий мобильный клиент.

Минимальная навигация:

```text
Repository
    ↓
Folder
    ↓
Document
    ↓
Reader
```

Точный Android UI можно адаптировать под Compose и сенсорное управление.

Не нужно искусственно копировать TUI.

---

## 14. Просмотр репозитория в Android

Клиент должен:

1. получить `repository.json`;
2. разобрать дерево;
3. показать каталоги;
4. показать документы выбранного каталога;
5. загрузить выбранный `.md` по HTTP;
6. открыть его в существующем Reader.

---

## 15. Refresh

В Repository View должна быть команда Refresh.

Она повторно запрашивает:

```text
repository.json
```

и перестраивает интерфейс.

Если возможно, сохраняется текущий выбор.

После успешного SFTP Upload Refresh должен выполняться автоматически.

---

## 16. Поиск

Поиск полезен, но для самого первого Android-среза может быть реализован сразу только если это не задерживает основную цель.

Поиск должен соответствовать Python-логике:

- по `name`;
- по `path`;
- без полнотекстового поиска содержимого.

Приоритет промежуточного этапа:

```text
просмотр + Reader + Upload
```

---

## 17. Ключевая функция — Upload с телефона

Это главная цель промежуточной Android-версии.

Пользователь должен иметь возможность выбрать локальный `.md`-файл и загрузить его в репозиторий.

Базовый сценарий:

```text
Repository View
    ↓
Upload
    ↓
Android file picker
    ↓
выбор .md
    ↓
выбор каталога назначения
    ↓
SFTP upload
    ↓
успех
    ↓
автоматический Refresh
```

---

## 18. Выбор локального файла

Использовать штатный Android Storage Access Framework.

Приложение не должно требовать прямого доступа ко всей файловой системе телефона.

Нужно поддерживать `content://` URI.

Ограничить выбор Markdown-файлами там, где это возможно.

---

## 19. Share / Open with mdview

Желательно предусмотреть возможность получить Markdown-файл от другого Android-приложения.

Типичный сценарий:

```text
ChatGPT
    ↓
скачанный .md
    ↓
Share / Open with
    ↓
mdview
```

После получения файла `mdview` может предложить загрузить его в репозиторий.

Если эта функция существенно увеличивает объём первой задачи, её можно сделать следующим маленьким этапом после базового Upload через file picker.

---

## 20. Выбор каталога назначения

Перед Upload пользователь должен выбрать, куда загрузить файл.

Использовать структуру каталогов текущего `repository.json`.

На первом этапе достаточно выбирать существующий каталог.

Создание нового каталога можно отложить.

Примеры назначения:

```text
/
hardware/
linux/
linux/network/
```

в пределах разрешённой структуры репозитория.

---

## 21. SFTP

Для записи используется SFTP.

Нужные настройки:

```text
sftp_host
sftp_port
sftp_user
sftp_root
auth_method
```

HTTP URL и SFTP host/path могут быть независимыми.

Например:

```text
HTTP:
http://ricaro.top/mdrepo/

SFTP:
host = hosting-server
root = /public_html/mdrepo
```

Android-клиент должен строить конечный SFTP-путь как:

```text
sftp_root + выбранный каталог + имя файла
```

---

## 22. Авторизация SFTP

Для промежуточной версии допустима простая схема.

Например:

- host;
- port;
- user;
- password.

Но пароль нельзя хранить открытым текстом в обычных настройках.

Предпочтительно:

- хранить секрет безопасным Android-механизмом;
- либо запрашивать пароль при Upload и хранить только в памяти сеанса.

Не помещать пароль в обычный JSON/DataStore без защиты.

---

## 23. Что Android пока НЕ должен уметь

На промежуточном этапе не требуется:

- несколько репозиториев;
- полноценный Sources View;
- History;
- Settings UI полного уровня Python-версии;
- удаление документов;
- создание каталогов;
- удаление каталогов;
- переименование;
- перемещение;
- серверный полнотекстовый поиск;
- offline synchronization;
- сложный cache;
- версии документов;
- комментарии;
- совместное редактирование.

---

## 24. Минимальные настройки Android-среза

Для ускорения разработки допустимо временно иметь один заранее заданный тестовый репозиторий.

Но архитектурно значения должны быть отделены от Repository View.

Минимально нужны:

```text
repository_url

admin.enabled
sftp_host
sftp_port
sftp_user
sftp_root
auth_method
```

Секрет хранится отдельно.

После стабилизации Android-клиента будет добавлена общая модель нескольких репозиториев из `SETTINGS.md`.

---

## 25. Ошибки

Android-клиент должен корректно обрабатывать:

- отсутствие сети;
- недоступный `repository.json`;
- повреждённый JSON;
- недоступный документ;
- отмену выбора файла;
- отсутствие доступа к URI;
- ошибку SFTP-соединения;
- неверную авторизацию;
- отсутствие прав записи;
- ошибку Upload;
- разрыв соединения.

Ошибка Upload не должна приводить к ложному Refresh с сообщением об успехе.

---

## 26. Безопасность Upload

При формировании серверного пути:

- нельзя позволять локальному имени файла выйти за пределы выбранного каталога;
- использовать только имя файла, а не произвольный локальный filesystem path;
- нормализовать серверный относительный путь;
- не позволять `../` выйти за `sftp_root`.

---

## 27. Проверка после Upload

После успешной передачи файла:

1. закрыть SFTP-операцию;
2. выполнить HTTP Refresh;
3. получить новый `repository.json`;
4. убедиться, что новый документ появился;
5. показать пользователю успешный результат.

Если файл передан по SFTP, но Refresh не удался, сообщить отдельно:

```text
Upload completed, repository refresh failed
```

Не считать Upload неуспешным только из-за ошибки последующего Refresh.

---

## 28. Предлагаемый порядок Android-разработки

### Этап A1 — read-only Repository

- один repository URL;
- загрузка `repository.json`;
- каталоги;
- документы;
- открытие в существующем Reader;
- Refresh.

### Этап A2 — Upload

- Android file picker;
- выбор `.md`;
- выбор существующего каталога;
- SFTP;
- Upload;
- автоматический Refresh.

### Этап A3 — удобство

- Share / Open with mdview;
- поиск;
- базовые настройки подключения.

После этого Android-версию уже можно использовать ежедневно.

## 29. Что продолжать в Python после Android-среза

После получения рабочей мобильной версии основная разработка Python может продолжиться.

Ближайшие направления:

- полноценное управление списком репозиториев;
- UI настроек;
- SFTP/admin-функции;
- Upload;
- удаление;
- создание каталогов;
- дальнейшая унификация поведения с Android.

## 30. Главный приоритет Android-этапа

Не пытаться сейчас перенести в Android весь функционал Python.

Главный практический сценарий:

```text
найти документ
→ прочитать
```

и:

```text
получить .md на смартфоне
→ выбрать его
→ загрузить в репозиторий
→ документ доступен на всех устройствах
```

Именно этот сценарий является критерием готовности промежуточной Android-версии.
